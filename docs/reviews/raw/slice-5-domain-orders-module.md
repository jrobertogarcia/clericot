## Slice 5: Domain: orders module
**Files reviewed:** 5 | **Findings:** 3 critical, 6 important, 6 suggestion, 3 nitpick

### Findings

**[CRITICAL] [BUG] internal/modules/orders/service.go:54 — Unchecked int64 arithmetic lets a client mint an order with a wrong or negative total.**
- **Issue:** `totalCents += int64(it.Quantity) * it.UnitPriceCents` has no overflow guard. Go wraps silently on signed overflow. `Quantity` is bounded only by `minimum:"1"` and `UnitPriceCents` only by `minimum:"0"` in `handler.go:17-18` — neither declares a `maximum`, so both accept any value representable in the Go type.
- **Failure scenario:** `POST /v1/orders` with `{"items":[{"product_name":"x","quantity":3037000500,"unit_price_cents":3037000500}]}`. The product is 9223372037000250000, which exceeds `MaxInt64` (9223372036854775807) and wraps to a large negative number. `totalCents` is negative, passes every check, and is persisted into `orders.total_cents` (BIGINT, no CHECK constraint in `sql/migrations/0004_orders.sql`). The order is now a credit. A second variant (`quantity: 4294967296, unit_price_cents: 4294967296`) yields exactly 0. The outbox event, the audit `Diff`, and the HTTP response all carry the corrupted figure.
- **Suggestion:** Validate per-item and running-total bounds in the domain layer (e.g. a `CreateOrderItemDTO.Validate()` in `entity.go` capping quantity and unit price), and detect overflow explicitly: after each multiply/add, check `if it.UnitPriceCents != 0 && line/it.UnitPriceCents != int64(it.Quantity)` or use `math/bits`. Add `maximum` tags in `handler.go` and CHECK constraints on the table as defense in depth.
- **Test contradiction:** `orders_test.go:45-60` only exercises quantity 1 and 2 at prices 200000/8000 and asserts `216000`. No test supplies a value anywhere near the overflow boundary, so the suite cannot observe the wrap.

**[CRITICAL] [BUG] internal/modules/orders/repository.go:73 — Silent `int` → `int32` narrowing breaks aggregate consistency between the order header and its items.**
- **Issue:** `Quantity: int32(item.Quantity)` truncates without a bounds check. `OrderItem.Quantity` is `int` (64-bit) while `sqlcgen.CreateOrderItemParams.Quantity` is `int32` (column is `INT`). The service computes `TotalCents` from the untruncated `int` but persists the truncated `int32`.
- **Failure scenario:** `{"quantity": 4294967297, "unit_price_cents": 100}`. The service computes `total_cents = 429496729700` and stores it on the header. The repository writes `quantity = 1` into `order_items`. `sum(quantity * unit_price_cents)` over the items is 100 while the header says 429496729700 — the aggregate is permanently inconsistent, and the transaction commits cleanly because the narrowed value satisfies the column type. With `quantity = 4294967296` the item row stores `0`, which the schema also permits (`quantity INT NOT NULL DEFAULT 1`, no CHECK).
- **Suggestion:** Reject out-of-range quantities in `entity.go` validation before they reach the repository, and make the conversion explicit and fallible in `CreateOrderItem` (return an error when `item.Quantity > math.MaxInt32 || item.Quantity <= 0`). Better still, type `OrderItem.Quantity` as `int32` so the domain and the column agree by construction. Add `CHECK (quantity > 0)` to the migration.
- **Test contradiction:** `orders_test.go` never asserts that `sum(items)` equals `order.TotalCents`, and uses only single-digit quantities, so no case crosses the int32 boundary.

**[CRITICAL] [DRIFT] internal/modules/orders/service.go:117-124, service.go:136-139, internal/modules/orders/module.go:19 — A nil `riverClient` silently disables both outbox staging and the compliance audit trail, and the production API wires exactly that.**
- **Issue:** The outbox insert is nested inside `if s.riverClient != nil { if tx != nil { ... } }`, and `audit.StageAuditLog` (`internal/platform/audit/audit.go:54-59`) returns `nil` when `riverClient == nil`. Neither path is unconditionally reached. `NewModule` accepts `riverClient *river.Client[pgx.Tx]` with no nil validation, so the degraded mode is indistinguishable from the healthy one. `cmd/api/main.go:98` calls `orders.NewModule(bundle.API, txManager, nil)`.
- **Failure scenario:** In the shipped API binary, every `POST /v1/orders` and `POST /v1/orders/{id}/cancel` returns 201/200 with a fully committed order and **zero** `audit.event.v1` rows and zero `orders.order_created.v1` outbox rows. Rule 9 mandates staging immutable audit CloudEvents atomically inside `RunInTx`; the SOC 2 / HIPAA trail the module advertises in its own doc comments (`service.go:37-38`, `handler.go:130`) does not exist. Downstream consumers scaffolding a module from this reference inherit the same silent-degradation shape. Rule 15's "compile-time verification and explicit wiring" is also defeated: the missing dependency is a runtime no-op rather than a build failure.
- **Suggestion:** Make the dependency mandatory. Have `NewService`/`NewModule` return an error (or panic at wiring time) when `riverClient` is nil, drop the `if s.riverClient != nil` guard from `CreateOrder`, and propagate `StageAuditLog`'s result unconditionally. If a nil client must be supported for tests, inject an explicit in-memory stager rather than overloading nil.
- **Test contradiction:** `orders_test.go:27` constructs the module with `NewModule(nil, testsuite.SharedTxManager, nil)` — the test itself runs in the degraded mode, so the suite is structurally incapable of catching a missing outbox or audit row.

**[IMPORTANT] [BUG] internal/modules/orders/service.go:207 — `CancelOrder` discards the audit-staging error with `_ =`, committing a state change with no audit record.**
- **Issue:** `_ = audit.StageAuditLog(txCtx, s.riverClient, tx, auditPayload)`. `CreateOrder` at line 137 correctly wraps and returns the same call's error; `CancelOrder` deliberately drops it. This is an asymmetry a reader will copy.
- **Failure scenario:** With a real `riverClient` wired (the intended production config once the previous finding is fixed), `river.InsertTx` fails for a non-fatal reason — a marshalling failure inside River's arg encoder, an advisory-lock timeout, or a `river_job` insert rejected by a queue-level constraint. `CancelOrder` returns `nil` from the closure, `RunInTx` commits, and the order is now `cancelled` in the database with no corresponding `audit.event.v1`. An auditor reconstructing who cancelled the order finds nothing. The caller receives HTTP 200 and no signal that anything went wrong.
- **Suggestion:** `if err := audit.StageAuditLog(...); err != nil { return fmt.Errorf("failed to stage audit log: %w", err) }`, matching `CreateOrder`. If a cancellation must be allowed to proceed without audit, that has to be an explicit, logged, documented decision rather than a bare `_ =`.

**[IMPORTANT] [DESIGN] internal/modules/orders/service.go:187 — No status state machine: any non-cancelled order, including `completed`, can be cancelled.**
- **Issue:** The only transition guard is `if ord.Status == OrderStatusCancelled`. `entity.go:11-17` declares five statuses but no `CanTransitionTo`/`Transition` method, and `project-layout.md` §3 states `entity.go` is where "validation methods" belong. The module is the reference implementation for transactional domain logic, so the absence of a transition table will be replicated across every scaffolded module.
- **Failure scenario:** An order reaches `completed` (goods shipped, payment captured by some future flow). A client calls `POST /v1/orders/{id}/cancel`. The check passes because the status is not `cancelled`, `UpdateOrderStatus` writes `cancelled`, and the order is now simultaneously fulfilled and cancelled with no compensating refund logic. The same applies to `paid`. Concurrently, two cancel requests both read `pending` inside separate transactions — the read-then-write in lines 182-191 has no `SELECT ... FOR UPDATE` and no optimistic version column, so both commit and two `orders.cancel` audit events are staged for one order.
- **Suggestion:** Add an explicit transition map to `entity.go` (e.g. `var allowedTransitions = map[OrderStatus][]OrderStatus{...}` plus `func (o *Order) CanTransitionTo(next OrderStatus) error`) and call it from `CancelOrder` before writing. For the race, either lock the row (`GetByIDForUpdate`) or make `UpdateOrderStatus` conditional (`WHERE ... AND status <> 'cancelled' RETURNING *`) and treat zero rows as `ErrOrderAlreadyCancelled`.
- **Test contradiction:** `orders_test.go:84-90` only covers cancel-then-cancel-again on a `pending` order. No test creates a `paid`/`completed` order (nothing in the module can produce one) and no test issues concurrent cancels, so neither gap is observable.

**[IMPORTANT] [PERF] internal/modules/orders/repository.go:153-154, 176 — The documented Rule 6 promise that the Bob search "preserves index scans" is not supported by the schema; the query sorts the whole tenant partition.**
- **Issue:** The doc comment claims preservation of index scans "on (tenant_id, user_id) and (status)". The available indexes are `idx_orders_tenant_user (tenant_id, user_id)` and `idx_orders_status (status)` (`sql/migrations/0004_orders.sql:13-14`). The query always adds `ORDER BY created_at DESC` with `LIMIT`, and `created_at` appears in no index. `deleted_at IS NULL` is also unindexed and there is no partial index.
- **Failure scenario:** The canonical call — `GET /v1/orders/search` with no filters, which the handler turns into tenant-only + `LIMIT 50` — forces Postgres to read every live row for the tenant (via `idx_orders_tenant_user` or a seq scan) and then perform a full sort before applying the limit. On the >50k-row table Rule 6 explicitly targets, this is O(n log n) per request with a disk sort, precisely the generic-plan pathology Rule 6 was written to avoid. Adding `status=pending` makes it worse: the planner may pick the low-selectivity `idx_orders_status` (which is not tenant-prefixed, contradicting Rule 4's "composite `(tenant_id, ...)` indexes") and then filter and sort. Rule 6 also mandates verifying plans with `EXPLAIN ANALYZE`; no such verification exists anywhere in the repo.
- **Suggestion:** Add `CREATE INDEX ... ON orders (tenant_id, created_at DESC) WHERE deleted_at IS NULL` and a tenant-prefixed `(tenant_id, status, created_at DESC)`, drop or re-prefix `idx_orders_status`, and either correct the doc comment to name the indexes that actually serve the query or remove the claim. Capture an `EXPLAIN ANALYZE` on a seeded large table as evidence, since Rule 6 requires it.

**[IMPORTANT] [SECURITY] internal/modules/orders/handler.go:39-40, internal/modules/orders/repository.go:178-186 — Unbounded `limit` and `offset` allow a single request to exhaust the connection and memory budget.**
- **Issue:** `Limit int32 \`query:"limit" default:"50"\`` declares no `maximum` and `Offset` declares no `maximum` either. The repository's only guard is `if filter.Limit > 0 { limit = filter.Limit }` — the default of 50 applies solely when the value is non-positive, never as a ceiling.
- **Failure scenario:** `GET /v1/orders/search?limit=2000000000`. Bob emits `LIMIT 2000000000`; the repository appends every returned row to `results` (line 222) with no cap, then `handler.go:182` allocates a parallel `[]OrderResponseBody` and serialises the lot. A tenant with a large order table drives the API pod OOM while holding an open transaction on the primary database for the duration — a direct violation of Rule 3's "never overload PostgreSQL". `offset=2000000000` is the cheaper variant: Postgres still materialises and sorts the full partition to discard it.
- **Suggestion:** Add `maximum:"200"` (or the agreed page size) and `minimum:"1"` to `Limit`, and clamp defensively in the repository: `if limit > maxSearchLimit { limit = maxSearchLimit }`. Cap `Offset` too, or migrate to keyset pagination on `(created_at, id)`, which also fixes the sort-stability finding below.

**[IMPORTANT] [PERF] internal/modules/orders/service.go:78-93 — Line items are inserted one round trip at a time inside the transaction, with no cap on item count.**
- **Issue:** The loop calls `s.repo.CreateOrderItem` once per item, and each call re-instantiates `sqlcgen.New(db)` and issues a separate `INSERT ... RETURNING *`. `CreateOrderInput.Body.Items` declares `minItems:"1"` but no `maxItems`, so the array length is bounded only by the request body size.
- **Failure scenario:** A client posts 50,000 one-cent items in a single request. The service executes 50,001 sequential network round trips while holding a write transaction open on the primary pool. At ~0.5 ms per round trip that is a ~25-second transaction pinning one pooled connection, blocking autovacuum's ability to reclaim on `orders`/`order_items`, and inflating `WriteTimeout` (30 s, `cmd/api/main.go`) into a coin flip — the request may time out client-side while the transaction keeps running server-side. Repeat concurrently and the pool is exhausted.
- **Suggestion:** Add `maxItems` to `CreateOrderInput` and a matching domain check. Replace the loop with a single multi-row insert (a `:copyfrom` sqlc query or one `INSERT ... VALUES (...),(...) RETURNING *`); the IDs and timestamps are already known client-side, so nothing depends on per-row `RETURNING`.

**[IMPORTANT] [CLARITY] internal/modules/orders/handler.go:232-234 — The default error branch destroys all diagnostic context and nothing logs it.**
- **Issue:** `httperr.Transform(err)` returns `NewInternal("An unexpected error occurred")` for any non-sentinel error (`internal/platform/httperr/problem.go:111-122`). The orders module never logs. The router stack (`internal/platform/router/router.go:27-28`) mounts only `RequestID` and `Recoverer` — there is no request logger and no Huma error hook.
- **Failure scenario:** A unique-constraint violation, an RLS policy denial, a pool timeout, or the `fmt.Errorf("failed to persist order item: %w", err)` wrap from `service.go:90` all collapse into an identical opaque 500. The carefully constructed wrap chain is discarded at the transport boundary and written nowhere. On-call sees a 500 rate with no order ID, no tenant ID, no SQLSTATE, and no way to distinguish a client-caused conflict from a database outage. Every scaffolded module inherits this.
- **Suggestion:** Log before transforming — `slog.ErrorContext(ctx, "orders request failed", "error", err, "operation", ...)` — inside `mapDomainError` (which requires threading a logger into `Handler`), or add a Huma/Chi error-logging middleware in the platform so all modules get it once. The redacted client-facing body is correct and should stay; the server-side loss is the defect.

**[SUGGESTION] [DESIGN] internal/modules/orders/service.go:108-124 — The staged River job's `Kind` is `domain.event.v1`, so the module's own `OrderCreatedWorker` can never receive it.**
- **Issue:** The service stages `events.DomainEvent`, whose `Kind()` returns `"domain.event.v1"` (`internal/platform/events/event.go:17-19`); the semantic type `"orders.order_created.v1"` lives only in the `Type` field. `cmd/worker/main.go:90` registers `orders.NewOrderCreatedWorker`, whose `OrderCreatedJobArgs.Kind()` is `"orders.order_created.v1"`.
- **Failure scenario:** An order is created. River dispatches the job by kind to `OutboxRelayWorker`, which relays it to Watermill. `OrderCreatedWorker.Work` is never invoked for any input the system can produce — it is registered, compiles, and is permanently dead. A developer adding order-creation side effects to that worker ships code that never runs and gets no compile-time or runtime signal.
- **Suggestion:** Pick one dispatch model and delete the other. If the Rule 7 outbox-relay path is canonical (it appears to be), remove `OrderCreatedJobArgs`/`OrderCreatedWorker` and its registration, and document that per-domain reaction happens on the Watermill side keyed off `DomainEvent.Type`. If a River-native worker is wanted, stage `OrderCreatedJobArgs` instead.

**[SUGGESTION] [BUG] internal/modules/orders/repository.go:89-98, 137-148 — `GetByID` and `UpdateStatus` ignore `deleted_at` while `Search` filters on it.**
- **Issue:** `Search` adds `sm.Where(psql.Quote("deleted_at").IsNull())` (line 160), but `sql/queries/orders.sql`'s `GetOrderByID` and `UpdateOrderStatus` filter only on `(id, tenant_id)`. The `Order` entity exposes `DeletedAt` and the fixtures already provide `WithOrderDeletedAt`, so soft delete is part of the intended model.
- **Failure scenario:** As soon as a soft-delete path exists (the tenant GDPR worker at `internal/platform/tenant/worker.go:99-103` already establishes this pattern for tenants), `GET /v1/orders/{id}` returns a deleted order at full fidelity while `GET /v1/orders/search` correctly hides it, and `POST /v1/orders/{id}/cancel` mutates a deleted row and stages an audit event for it. The two endpoints disagree about whether the resource exists.
- **Suggestion:** Add `AND deleted_at IS NULL` to both `GetOrderByID` and `UpdateOrderStatus` in `sql/queries/orders.sql` (the existing `pgx.ErrNoRows` → `ErrOrderNotFound` mapping then gives the right 404 for free), or remove `deleted_at` from the search predicate and the entity if soft delete is not actually in scope.

**[SUGGESTION] [BUG] internal/modules/orders/repository.go:176, 184-186 — `ORDER BY created_at DESC` over a non-unique column with OFFSET paging can duplicate or skip rows across pages.**
- **Issue:** `created_at` has no uniqueness guarantee and no tiebreaker is appended. Postgres gives no stable ordering among equal sort keys, and a fresh plan is chosen per page request.
- **Failure scenario:** A batch import (or any two orders created within the same clock tick — `service.go:58` uses a single `time.Now().UTC()` per order, and coarse-resolution clocks make ties reachable) produces several rows sharing `created_at`. A client pages `offset=0&limit=50` then `offset=50&limit=50`. Rows tied at the page boundary may be returned on both pages or on neither, silently. Concurrent inserts during paging shift everything and compound it.
- **Suggestion:** Append a deterministic tiebreaker — `sm.OrderBy("created_at").Desc()` followed by `sm.OrderBy("id").Desc()` — and, better, move to keyset pagination (`WHERE (created_at, id) < ($cursor_ts, $cursor_id)`), which also resolves the deep-offset cost noted above.

**[SUGGESTION] [DRIFT] internal/modules/orders/handler.go:88-147 — Operations declare neither `Security` nor `Errors`, so the OpenAPI contract misrepresents every orders endpoint.**
- **Issue:** All four `huma.Operation` values omit `Security` and `Errors`. Rule 2 requires that "documentation, validation, serialization and error contracts are strictly derived from Go types", and `stack-standards.md` names `SecuritySchemes` integration as part of the Huma tier.
- **Failure scenario:** A client generates an SDK from `/openapi`. Every orders operation is described as unauthenticated and as returning only 200/201, so the generated client sends no `Authorization` header and has no typed handling for the 401 (`ErrUnauthenticated`), 404 (`ErrOrderNotFound`), 409 (`ErrOrderAlreadyCancelled`), or 400 (`ErrInvalidOrderItems`) the handler demonstrably produces. Integration fails at runtime against a spec that claimed otherwise.
- **Suggestion:** Set `Security: []map[string][]string{{"bearer": {}}}` (registering the scheme in the Huma config) and `Errors: []int{400, 401, 404, 409}` per operation. This is the highest-leverage fix in the slice for downstream copies, since the scaffolder will propagate whichever shape is here.

**[SUGGESTION] [DESIGN] internal/modules/orders/service.go:50-55 — Line-item validation is incomplete and lives outside `entity.go`.**
- **Issue:** The loop checks only `Quantity <= 0 || UnitPriceCents < 0`. `ProductName` is never validated despite `ErrInvalidOrderItems` reading "must contain at least one valid line item". The `minLength:"1"` constraint exists only on the HTTP DTO, and `project-layout.md` §3 assigns validation methods to `entity.go`.
- **Failure scenario:** Any non-HTTP caller — another module invoking `Service.CreateOrder` via the exported service interface that `project-layout.md` §2.3 explicitly endorses for inter-module communication, or a seeder, or the CLI — creates an order with `ProductName: ""`. The row persists, the invoice renders a blank line, and no error is raised. The service is the module's public contract but enforces a weaker invariant than the HTTP edge.
- **Suggestion:** Move the rules into `entity.go` as `func (d CreateOrderItemDTO) Validate() error`, include a non-empty/length check on `ProductName` and the numeric bounds from the overflow finding, and have `CreateOrder` call it. Keep the Huma tags for schema documentation; the domain check becomes the enforcement point.

**[SUGGESTION] [CLARITY] internal/modules/orders/repository.go:155-239 — `Search` never populates `Items`, so the same resource has two shapes depending on the endpoint.**
- **Issue:** `Search` builds `Order` values with `Items` left nil, while `GetByID` populates them. `handler.go:58` marks the field `omitempty`, so the difference is invisible in the schema.
- **Failure scenario:** A client renders an order list from `/v1/orders/search` and finds no `items` key, then fetches `/v1/orders/{id}` for the same order and gets a populated `items` array. Consumers cannot tell "this order has no line items" from "this endpoint does not return line items" — and the former is impossible given `minItems:"1"` on creation. A client that assumes list parity computes an empty cart.
- **Suggestion:** Either introduce a distinct `OrderSummary` type for search results so the omission is explicit in the contract, or batch-load items for the returned page with a single `WHERE order_id = ANY($1)` query and group in Go. Do not add a per-order `ListOrderItems` call in a loop — that would reintroduce the N+1 the current code happens to avoid.

**[NITPICK] [CLARITY] internal/modules/orders/repository.go:111-129 — `Repository.ListOrderItems` is dead code.**
- **Issue:** No caller exists; `GetByID` invokes `queries.ListOrderItems` directly at line 100 instead. In a template that gets copied per module, an unused exported method reads as sanctioned API surface.
- **Failure scenario:** A developer building the batch item-loading fix above reaches for `ListOrderItems`, calls it once per order in a loop, and ships an N+1 — the method's per-order signature actively invites it.
- **Suggestion:** Delete it, or repurpose it as the batch `ListOrderItemsByOrderIDs` the search path needs.

**[NITPICK] [CLARITY] internal/modules/orders/entity.go:12, 14, 16 — `OrderStatusDraft`, `OrderStatusPaid`, and `OrderStatusCompleted` are unreachable.**
- **Issue:** `CreateOrder` always writes `pending`; `CancelOrder` is the only transition and always writes `cancelled`. No code path produces the other three (only `tests/fixtures` references `Paid`).
- **Failure scenario:** `GET /v1/orders/search?status=paid` is documented as valid in `handler.go:35` and always returns an empty list, with no way for the caller to distinguish "no paid orders" from "this status is not implemented."
- **Suggestion:** Either implement the transitions (which the state-machine finding above would formalise) or trim the enum to what the module supports and update the `status` query-param doc string accordingly. Adding an `enum:"draft,pending,paid,cancelled,completed"` tag to `SearchOrdersInput.Status` would at least surface the vocabulary in the schema.

**[NITPICK] [CLARITY] internal/modules/orders/service.go:58, 114, 133 and handler.go:159-165 — Multiple clock reads per operation, and `max_amount=0` is inexpressible.**
- **Issue:** `CreateOrder` reads the clock three times (`now`, `time.Now().Unix()`, `time.Now().UTC()`), so the row timestamp, the event timestamp, and the audit timestamp can disagree. Separately, `if input.MinAmount > 0` / `if input.MaxAmount > 0` use zero as the "absent" sentinel.
- **Failure scenario:** Correlating an `audit.event.v1` to its order row by timestamp requires a fuzzy window rather than an exact match. For the filter: `?max_amount=0` (find zero-total orders) is silently dropped and returns all orders instead of the intended subset — a filter that appears to be applied but is not.
- **Suggestion:** Reuse the single `now` value for all three timestamps. For the filter, either accept pointer/optional query params or document that 0 is treated as unset.

### Strengths
- The Bob search is genuinely injection-free: every value flows through `psql.Arg` and every identifier (`sm.From("orders")`, `psql.Quote("tenant_id")`, `sm.OrderBy("created_at")`) is a compile-time literal. Predicate composition via appended `sm.Where` mods correctly ANDs, and the mandatory `tenant_id` predicate is added before any optional filter, so no filter combination can drop tenant scoping. This is the right shape to copy 50 times.
- Defence in depth on tenancy: the repository filters `tenant_id` in SQL *and* `RunInTx` sets `app.current_tenant_id` for RLS. Neither layer is load-bearing alone, and `service.go` consistently derives the tenant from the authenticated principal rather than from client input.
- Transaction ordering in `CreateOrder` is correct: header, items, outbox event, and audit are all staged before commit, so a failure at any step rolls back the whole aggregate. Staging via `InsertTx` on the context-resolved `pgx.Tx` also composes correctly with `RunInTx`'s savepoint path.
- `GetByID` deliberately loads items with a single bounded second query rather than per-item lookups, and `mapDomainError` cleanly separates domain sentinels from transport concerns without leaking internal error text to clients.

### Out-of-slice observations
- `internal/platform/database/tx.go:37-65`: the nested savepoint branch never invokes `TenantSetter`, so a module entering an existing transaction that was opened without a tenant will run its queries with no `app.current_tenant_id` set.
- `internal/platform/audit/audit.go:54-59`: `StageAuditLog` returning `nil` on a nil client or nil tx is the enabling mechanism for the audit-trail gap; the platform function should error rather than no-op.
- `cmd/api/main.go:98`: passes `nil` as the orders River client, which is what makes the outbox/audit gap live in production rather than hypothetical.
- `internal/platform/router/router.go:24-44`: no request/error logging middleware and a permissive CORS origin list (`https://*`, `http://*`) combined with `AllowCredentials: true`.
- `internal/modules/orders/orders_test.go:27`: the module under test is constructed with a nil River client, so no assertion in the suite can observe outbox or audit staging; the lifecycle test also never asserts that `sum(items)` reconciles with `order.TotalCents`.
- `internal/modules/orders/worker.go`: `OrderCreatedWorker` is unreachable given the `Kind` mismatch described above (filed against `service.go`, which chooses the staged type).
- `database.TxManager` offers no read-only transaction mode, so `GetOrderByID` and `SearchOrders` each open a read-write transaction on the primary pool for a pure read.
- The orders module uses none of the Rule 10 two-tier cache despite being the reference implementation; `GetOrderByID` hits the database unconditionally.
