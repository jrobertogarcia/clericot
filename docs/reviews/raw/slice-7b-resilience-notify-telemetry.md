[CRITICAL] [DRIFT] internal/platform/resilience/resilience.go:286 — `NewHTTPRetryPolicy` retries HTTP 429, the exact status Rule 12 requires be ignored.
- **Issue:** The builder starts from `failsafehttp.NewRetryPolicyBuilder()`, whose baked-in predicate returns `true` for `StatusTooManyRequests` (see `failsafehttp/policy.go`, "Retry on 429"). Line 294 then calls `builder.HandleIf(cfg.HandleIf)`. In failsafe-go, `HandleIf` **appends** to `failureConditions` (`policy/policy.go:53-57`) and `IsFailure` returns true if *any* condition matches (`util.AppliesToAny`). `HTTPRetryPredicate` returning `false` for 429 therefore cannot suppress the library default — the two are OR'd. Net effect: 429 is retried up to `MaxRetries` times. Golden Rule 12 and stack-standards.md:35/81 all state failsafe-go must be "explicitly configured to ignore HTTP 429 status codes."
- **Failure scenario:** A tenant's Stripe/SendGrid integration gets throttled and starts returning `429`. Each logical call becomes 4 upstream calls (1 + 3 retries). At 200 rps the framework turns a 200 rps throttle into 800 rps against an upstream that just said "stop" — the textbook retry-amplification pattern Rule 12 exists to prevent. If the upstream returns `Retry-After: 300`, `failsafehttp.DelayFunc` takes precedence over the configured `MaxBackoffDelay` (`retryexecutor.go:132`), so the caller's goroutine parks for ~5 minutes per attempt, ignoring the 2s cap the config appears to promise.
- **Suggestion:** Do not build on `failsafehttp.NewRetryPolicyBuilder()`. Use `retrypolicy.NewBuilder[*http.Response]()` and set the single predicate you want (`HandleIf(HTTPRetryPredicate)` plus `AbortOnErrors(context.Canceled)`), or keep the failsafehttp base and add `AbortIf(func(r *http.Response, _ error) bool { return r != nil && r.StatusCode == 429 })` — abort conditions are checked independently and do win. Also clamp the `Retry-After` delay to `MaxBackoffDelay`. Document that `WithHandleIf` can only widen, never narrow, the failure set (line 244's doc comment, "configures the failure predicate that triggers a retry", is materially wrong today).
- **Test contradiction:** `resilience_test.go` has three 429 assertions but all of them exercise the **circuit breaker** path (`TestHTTPCircuitBreakerPredicate`, `TestCircuitBreaker_429ResponsesDoNotTrip` — which builds `NewHTTPClient(cb)` with no retry policy). `TestRetryPolicy_TransientErrors` uses only `503`. No test ever sends a 429 through a retry policy and counts server hits, so the suite's "429 is ignored" claim covers only half of Rule 12.

[CRITICAL] [BUG] internal/platform/resilience/resilience.go:416 — Response bodies from discarded retry attempts are never drained or closed, leaking connections.
- **Issue:** `failsafehttp` does not close the body of an attempt whose result the retry policy rejects — `grep 'Body.Close'` over the non-test sources of failsafe-go v0.9.7 returns nothing. `doRequest` wraps each attempt's body in `bodyWithCancel` and returns it as the policy result; when the retry policy loops, that response is simply abandoned. In `net/http`, a response body that is neither read to EOF nor closed keeps its persistent connection checked out of the pool indefinitely (it is not returned on GC — there is no finalizer). `NewRoundTripper`/`NewHTTPClient` hand this behavior to every consumer with no mitigation.
- **Failure scenario:** Service uses `NewHTTPClient(NewHTTPRetryPolicy())` (the documented usage) against an upstream in a 5xx storm. Each inbound request produces 3 abandoned `*http.Response` values whose bodies are never closed, so 3 TCP connections per request are pinned until the *server* times them out. At 100 rps that is 300 unreclaimable connections/sec; `http.DefaultTransport` sets no `MaxConnsPerHost`, so the process climbs to its file-descriptor limit and then fails every outbound call — including to healthy dependencies sharing `DefaultTransport`. The application's `/readyz` may stay green throughout.
- **Suggestion:** Drain and close discarded responses in the framework wrapper, not in user code. Set a default `OnRetry` inside `NewHTTPRetryPolicy` that does `if r := event.LastResult(); r != nil && r.Body != nil { io.Copy(io.Discard, io.LimitReader(r.Body, 64<<10)); r.Body.Close() }`, and compose it with any user-supplied `WithOnRetry` rather than letting the user option replace it.
- **Test contradiction:** `TestRetryPolicy_TransientErrors` (line 200) retries two `503`s and passes. It asserts only `attempts == 3` and the final body. `httptest.Server.Close()` in the deferred cleanup force-closes all lingering connections, and the test never inspects connection counts or runs long enough to exhaust anything, so a leak of two connections is indistinguishable from correct behavior.

- **Issue:** The package exports 23 functional-option constructors, 3 option types, 3 config structs, 8 constants, and 5 factories. `grep -rn --include="*.go" "resilience\."` finds callers in exactly one file: `resilience_test.go`. Change the two policy factories to take a `func(builder)` customizer (`NewHTTPCircuitBreaker(func(b circuitbreaker.Builder[*http.Response]) { b.WithFailureRateThreshold(...) })`) instead of 15 hand-mirrored options — that exposes 100% of the upstream builder for less code than the current subset. Delete the entire `WithGeneric*` family and `NewCircuitBreaker[R]`/`NewRetryPolicy[R]` until a caller exists; `Execute` already accepts raw `failsafe.Policy[R]`, so generic users can call failsafe-go directly. Unexport the three config structs.

[IMPORTANT] [DRIFT] internal/platform/resilience/resilience.go:424 — `NewHTTPClient` returns a client with no timeout, and the Timeout/Bulkhead policies the docs promise do not exist.
- **Issue:** `&http.Client{Transport: ...}` leaves `Timeout` at its zero value (no deadline) over `http.DefaultTransport`, which sets no `ResponseHeaderTimeout` either. The package also has no timeout or bulkhead constructor at all, though stack-standards.md:35 specifies "In-process composable policies (Retry, **Circuit Breaker, Timeout, Bulkhead**)" and failsafe-go ships both `timeout` and `bulkhead` packages.
- **Failure scenario:** Upstream completes the TCP handshake then stalls before sending response headers (a common overload/LB-blackhole signature). The calling goroutine blocks forever; the circuit breaker never fires because no failure is ever recorded; the connection is never released. During Rule 13's 5-phase shutdown, `Coordinator.Shutdown` cannot drain these in-flight requests, so the 25-second budget is overrun and Kubernetes SIGKILLs at 30s mid-transaction.
- **Suggestion:** Add a `WithClientTimeout` (default ~10-30s) applied to the returned `*http.Client`, and/or add `NewTimeout(d)` returning a `timeout.Timeout[*http.Response]` policy so per-attempt timeouts compose inside the retry policy. Document that a client without a timeout must never be used in request-path code.

[IMPORTANT] [BUG] internal/platform/resilience/resilience.go:49 — Retry policies retry `circuitbreaker.ErrOpen`, converting fast-fail into slow-fail.
- **Issue:** `HTTPRetryPredicate` returns `true` for any non-nil error, and the failsafehttp default predicate does the same for all non-`url.Error` errors. When policies are composed as `NewHTTPClient(retry, cb)` — the correct order — the breaker is inner, so once it opens it returns `ErrOpen` to the retry policy, which classifies it as retryable. Neither factory installs `AbortOnErrors(circuitbreaker.ErrOpen)`.
- **Failure scenario:** Upstream is fully down, breaker is open. Every inbound request now burns 3 retries against an already-open breaker: ~100ms + 200ms + 400ms of pure sleep, ~700ms per request, and still returns `ErrOpen`. At 500 concurrent requests this is 350 goroutine-seconds of parked work per second and a p99 that jumps from ~1ms (the entire point of a circuit breaker) to 700ms+, with the request queue backing up behind it.
- **Suggestion:** Default `AbortIf` in both `NewHTTPRetryPolicy` and `NewRetryPolicy` to abort on `circuitbreaker.ErrOpen` (and on `context.Canceled`/`context.DeadlineExceeded` for the generic variant, which today has no abort conditions at all).

[IMPORTANT] [DESIGN] internal/platform/resilience/resilience.go:416 — Policy composition order is silently load-bearing and completely undocumented.
- **Issue:** `NewRoundTripper(inner, policies ...failsafe.Policy[*http.Response])` forwards to `failsafe.With(policies...)`, where **the first policy is outermost** (`failsafe.go:95-101`: `With(fallback, retryPolicy, circuitBreaker)` ⇒ `Fallback(RetryPolicy(CircuitBreaker(fn)))`). Nothing in the doc comments of `NewRoundTripper`, `NewHTTPClient`, `NewHTTPClientWithTransport`, or `Execute` mentions that argument order changes semantics. The two orders are not merely different, they are opposite.
- **Failure scenario:** A downstream developer writes the intuitive `resilience.NewHTTPClient(cb, retry)` — circuit breaker first, "because it's the outer guard." This yields `CircuitBreaker(RetryPolicy(fn))`: the breaker now observes one outcome per 4 attempts, so `FailureThreshold=5` requires 20 upstream failures instead of 5, and retries keep hammering the upstream even after the breaker conceptually should have stopped them. The code compiles, the tests (which only ever pass a single policy) pass, and the breaker is quietly ~4x less sensitive in production.
- **Suggestion:** Either document the ordering contract prominently on all four entry points with an explicit "outermost first" example, or remove the ambiguity entirely with a typed constructor such as `NewResilientHTTPClient(cfg ResilienceConfig)` that builds `retry, breaker` in the correct order internally and never exposes a variadic policy slice.

[SUGGESTION] [DESIGN] internal/platform/resilience/resilience.go:280 — Retries are applied uniformly to every HTTP method, including non-idempotent POST/PUT/PATCH.
- **Issue:** `HTTPRetryPredicate` keys only on status code and error, never on `req.Method`. `failsafehttp.doRequest` deliberately buffers and replays the request body (`bodyReader`) so POSTs *will* be retried. There is no per-method filter, no `Idempotency-Key` support, and no warning in the doc comment. - **Failure scenario:** `POST /v1/charges` reaches the payment provider, the charge is created, and the `200` response is lost to a gateway timeout that surfaces as a transport error or `504`. `HTTPRetryPredicate` returns `true`, the buffered body is replayed, and the customer is charged 2-4 times. - **Suggestion:** Default the retry predicate to retry only idempotent methods (`GET`, `HEAD`, `OPTIONS`, `TRACE`, `PUT`, `DELETE`), exposing the request method by using `failsafehttp` execution context or by keying the policy per-client. At minimum, document the hazard on `NewHTTPRetryPolicy` and `NewHTTPClient`.

[SUGGESTION] [PERF] internal/platform/resilience/resilience.go:69 — A jitter factor of 0.1 is too narrow to decorrelate a fleet-wide retry herd.
- **Issue:** `DefaultJitterFactor = 0.1` maps to `util.RandomDelayFactor(delay, 0.1, rand)` = `delay * (1 ± 0.1)` — a ±10% spread around a deterministic exponential schedule. Standard practice for shared-upstream retry storms is full or decorrelated jitter (uniform over `[0, backoff]`).
- **Failure scenario:** An upstream returns `503` to 50 pods simultaneously at t=0 (a deploy, a failover, a shared-dependency blip). All 50 first retries land in the window 90-110ms, all second retries in 180-220ms. The upstream, which was just recovering, is hit by three tightly-synchronized bursts of 50 and re-fails, extending the outage. A ±10% spread over a 100ms base is a 20ms window — effectively no decorrelation.
- **Suggestion:** Raise `DefaultJitterFactor` to ~0.5, or switch to `WithDelayFactorRandom`-style full jitter over `[0, computedDelay]`.

[SUGGESTION] [DESIGN] internal/platform/resilience/resilience.go:61 — `DefaultSuccessThreshold = 1` lets a single lucky probe close the breaker onto a still-degraded upstream.
- **Issue:** After `DefaultCircuitDelay` (10s), one successful half-open probe returns the breaker to closed and restores 100% of traffic. There is no ratio-based alternative exposed (`circuitbreaker.Builder.WithSuccessThresholdRatio` exists upstream but is not surfaced — see the YAGNI finding).
- **Failure scenario:** An upstream is degraded, not down: it succeeds ~40% of the time. Breaker opens after 5 consecutive failures, waits 10s, sends one probe, hits the 40% that works, and closes. Full traffic resumes, 5 more consecutive failures arrive within milliseconds, breaker reopens. The result is a 10-second flap cycle that provides essentially no protection while generating continuous state-change noise — and each flap cycle also drags every in-flight caller through the 700ms `ErrOpen` retry penalty described above.
- **Suggestion:** Raise the default success threshold to 3-5, or expose `WithSuccessThresholdRatio` so consumers can require e.g. 3-of-5 successful probes.

[NITPICK] [CLARITY] internal/platform/resilience/resilience.go:73,206,311 — Three exported config structs that no exported function accepts.
- **Issue:** `CircuitBreakerConfig`, `HTTPRetryConfig`, and `GenericRetryConfig[R]` are exported with exported fields, but every constructor takes `...Option` and builds the config internally. A caller can populate one and has nowhere to pass it.
- **Failure scenario:** A downstream developer reads the godoc, sees `CircuitBreakerConfig{FailureThreshold: 10}`, builds it, then discovers there is no `NewHTTPCircuitBreakerFromConfig` — wasted time and a confusing public surface replicated across every scaffolded repo.
- **Suggestion:** Unexport all three, or add config-accepting constructors and unexport the option families.

[NITPICK] [BUG] internal/platform/resilience/resilience.go:56 — `HTTPRetryPredicate` retries `501 Not Implemented`, a permanently-failing status.
- **Issue:** `resp.StatusCode >= http.StatusInternalServerError` includes 501. failsafe-go's own predicate explicitly excludes it (`resp.StatusCode >= 500 && resp.StatusCode != http.StatusNotImplemented`), so the framework's predicate is strictly worse than the library default it was written to replace.
- **Failure scenario:** Client calls an endpoint the upstream does not implement. Each call becomes 4 calls plus ~700ms of backoff before returning the same 501 it would have returned immediately. Pure latency and load with a guaranteed-zero success rate.
- **Suggestion:** Exclude 501 (and consider 505) from the retry predicate.

[NITPICK] [DRIFT] internal/platform/notify/notify.go:1-81 — The package delivers email only, while the docs describe a multi-channel dispatcher.
- **Issue:** stack-standards.md:27 specifies "Email (SMTP/SES/Resend), **SMS (Twilio), Webhooks**, and Mailpit"; project-layout.md:36 says "go-mail & multi-channel dispatcher." The implementation has one `EmailMessage` type and two email methods.
- **Failure scenario:** A team plans an MFA-over-SMS feature against the documented capability matrix, budgets zero days for it, and discovers at implementation time that only email exists — the classic cost of a spec that describes intent as fact.
- **Suggestion:** Either narrow the two doc entries to "email dispatcher (SMTP/SES/Resend + Mailpit)", or introduce a `Channel` interface with email as the first implementation so the extension point at least exists.

### Strengths

- `HTTPCircuitBreakerPredicate` (resilience.go:28-45) is genuinely well-executed: the ordering of the checks is correct, the `resp == nil` guard is present, the doc comment states the Rule 12 rationale for each branch rather than restating the code, and the 429/4xx-vs-5xx distinction is exactly right for circuit breaking. It is the one part of the package that earns its place, and it is correspondingly the best-tested.
- `Execute` (resilience.go:439) handles the nil-function case explicitly with a typed zero value instead of panicking, and threads `exec.Context()` (not the outer `ctx`) into the wrapped function — which is the subtle-but-correct choice, since it gives the callee the per-attempt cancellation context rather than the parent.
- `NewRoundTripper`/`NewHTTPClientWithTransport` defaulting a nil transport to `http.DefaultTransport` keeps the zero-value path usable and makes the transport injectable for testing — a good seam for a template package.
- `telemetry.InitTracer` returning the `*sdktrace.TracerProvider` to the caller (rather than only setting the global) is the right shape: it lets `app.Coordinator` own shutdown ordering within the Rule 13 budget, and `coordinator.go:138` correctly nil-guards it.

### Out-of-slice observations

- `internal/platform/notify/notify_test.go:14-27` asserts that a nil-client dispatcher returns `nil` from both `EnqueueEmail` and `SendDirect`, encoding the silent-drop bug as the package contract; a fix requires changing this test.
- `internal/platform/telemetry/telemetry_test.go` asserts only non-nil-and-shuts-down-cleanly, which is satisfied by a tracer provider that exports nothing; it cannot detect the missing exporter.
- `internal/platform/resilience/resilience_test.go` never composes two policies in one client, so the order-sensitivity of `failsafe.With` is entirely uncovered, and `TestRetryPolicy_TransientErrors` never sends a 429 through a retry policy.
- `internal/config/config.go:59` declares `OTelConfig.Endpoint` (`OTEL_EXPORTER_OTLP_ENDPOINT`) which is parsed but read by no code in the repository — a dead configuration knob.
- `cmd/worker/main.go` never calls `telemetry.InitTracer`, so the worker daemon has no tracer provider at all (only `InitLogger`); River/Asynq/Watermill job execution is untraced even once an exporter is added.
- `cmd/api/main.go:64-70` and `cmd/worker/main.go:55-60` swallow `redis.ParseURL` errors (`if err == nil { rdb = ... }`), leaving `rdb` nil on a malformed URL — this is the upstream cause that makes notify's nil-client path reachable in production.
- `internal/modules/auth/worker.go:14` defines a second, parallel email task type outside `platform/notify`, which is the concrete precedent scaffolded modules will copy.
- `docs/architecture/stack-standards.md:35` lists Timeout and Bulkhead as in-scope failsafe-go policies; neither exists in the codebase, so the technology matrix overstates delivered capability for this tier.
