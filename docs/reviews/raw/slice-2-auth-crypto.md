## Slice 2: Auth & crypto
**Files reviewed:** 7 | **Findings:** 4 critical, 9 important, 2 suggestion, 2 nitpick

### Findings

[CRITICAL] [SECURITY] internal/platform/auth/token.go:125 — `HTTPMiddleware` silently downgrades an invalid, expired, or revoked token to an anonymous request, and the package ships no deny-by-default counterpart.
- **Issue:** The middleware attaches a principal on success and does nothing on failure (`if principal, err := s.ValidateToken(...); err == nil && principal != nil`). `ErrInvalidToken` and `ErrTokenRevoked` are discarded, no 401 is written, no `WWW-Authenticate` header is set, and no metric or log is emitted. `internal/platform/auth` exports no `RequireAuth` middleware and registers no Huma `SecuritySchemes`, so authorization is entirely opt-in per handler.
- **Failure scenario:** Run `clericot make:module billing`. The generated handler (cmd/clericot/main.go:325-335) reads `tenantID := input.Body.TenantID` and the generated service (cmd/clericot/main.go:223-247) calls `tenant.WithTenant(ctx, dto.TenantID)` with no `PrincipalFromContext` check at all. An unauthenticated `POST /v1/billing` with `{"tenant_id":"victim-tenant","name":"x"}` and no Authorization header passes both middlewares and writes a row into the victim tenant. Sending a garbage or expired Bearer token produces the identical result because the failure path is indistinguishable from "no credentials". The same chain reaches `tenant.Middleware`, which only calls `HasTenantAccess` when `principal != nil` (internal/platform/tenant/middleware.go:19), so a nil principal makes `X-Tenant-ID` fully trusted.
- **Suggestion:** Split the concern. Keep an optional-auth extractor, but have it reject with 401 when a Bearer credential is present and invalid (present-but-bad is never the same as absent), and add an exported `RequireAuth` / `RequireTenantAccess` middleware plus a Huma `SecuritySchemes` registration that the scaffolder wires into every generated route by default.
- **Test contradiction:** `TestTokenService_ValidateInvalidToken` (auth_test.go:66) covers `ValidateToken` in isolation and asserts it returns `ErrInvalidToken`. No test exercises `HTTPMiddleware`, so nothing observes that the error is swallowed by the caller one frame up.

[CRITICAL] [DRIFT] internal/platform/security/tink.go:19 — The only Tink constructor generates an ephemeral in-process keyset; the mandated `KmsEnvelopeAead` engine does not exist.
- **Issue:** Rule 11 and stack-standards.md require `KmsEnvelopeAead` envelope encryption via AWS KMS, GCP KMS, or Vault. `NewTinkLocalEngine` calls `keyset.NewHandle` to mint a brand new AES-256-GCM key on every call and holds it only in memory. There is no KMS-backed constructor, no keyset serialization or loading helper, and no key-handle export, so there is no path from this package to the documented behavior.
- **Failure scenario:** A downstream service encrypts a PII column through `EnvelopeEngine.Encrypt` on API replica A. Replica B was started with a different random keyset, so every `Decrypt` there returns "decryption failed". After a rolling deploy, all replicas hold new keys and 100% of previously written ciphertext is permanently unrecoverable. The doc comment says "for local development and integration tests", but since no other constructor exists, the only way to satisfy the documented envelope-encryption requirement is to use this one.
- **Suggestion:** Add `NewTinkKMSEngine(ctx, kekURI string, ...)` using `aead.NewKMSEnvelopeAEAD2` with the registered KMS client, plus keyset load/save helpers bound to a keyset URI in config. Rename the local constructor to something that cannot be mistaken for production (`NewInsecureEphemeralEngine`) or gate it behind a build tag.
- **Test contradiction:** `TestTinkEngine_LocalAEAD` encrypts and decrypts through the *same* engine instance inside one test function, which is the one arrangement in which a per-instance ephemeral key is invisible. A second `NewTinkLocalEngine()` decrypting the first engine's ciphertext would fail.

[CRITICAL] [SECURITY] internal/platform/auth/token.go:103 — `RevokeToken` reports success while revoking nothing when Redis is absent.
- **Issue:** `if s.redis == nil { return nil }` returns a nil error, which is indistinguishable from a successful revocation. `IsTokenRevoked` mirrors this by returning `(false, nil)`. Redis is optional at construction (`NewTokenService(secret, rdb)` accepts nil), and cmd/api/main.go:65-71 leaves `rdb` nil whenever `REDIS_URL` is empty *or* `redis.ParseURL` fails, with the parse error dropped on the floor.
- **Failure scenario:** An operator deploys with a typo in `REDIS_URL` (for example a missing `redis://` scheme). `ParseURL` errors, `rdb` stays nil, the process boots healthy. A user reports a stolen token; the support tooling calls `RevokeToken`, gets `nil`, and logs "token revoked". The token keeps working for its full 24 hour TTL (the TTL is hardcoded at internal/modules/auth/service.go:83 and 133). Rule 11's "instant Redis revocation blocklist" guarantee is silently void with no signal anywhere.
- **Suggestion:** Make Redis mandatory for `TokenService`: return an error from `NewTokenService` when `rdb == nil`, or add an explicit `ErrRevocationUnavailable` returned by both `RevokeToken` and `IsTokenRevoked` so callers must decide. A nil dependency must never be encoded as a successful security operation.

[CRITICAL] [DRIFT] internal/platform/security/rate_limiter.go:37 — The limiter exposes no HTTP middleware and is wired nowhere, leaving unauthenticated Argon2id (64 MiB x 4 lanes per call) exposed at the edge.
- **Issue:** Rule 9 requires enforcing "edge rate limiting in front of Argon2id password hashing". `RateLimiter` offers only `Allow(ctx, key, rps) (bool, error)`; it provides no `func(http.Handler) http.Handler`, no key extractor (IP, tenant, principal), and no 429 response with `Retry-After`. Nothing outside its own test constructs it: cmd/api/main.go:94 mounts only `RequestID`, `Recoverer`, CORS, the token middleware, and the tenant middleware.
- **Failure scenario:** `POST /v1/auth/register` and `POST /v1/auth/login` reach `security.HashPassword` / `security.VerifyPassword` with `DefaultArgon2Params` (m=64 MiB, p=4). 100 concurrent unauthenticated requests allocate roughly 6.4 GiB and 400 hashing goroutines; a 2 GiB container is OOM-killed in under a second by a single attacker on a laptop. There is no code path in the framework that could have prevented it, since no route can currently consume the limiter.
- **Suggestion:** Export `func (l *RateLimiter) Middleware(keyFn func(*http.Request) string, rps int) func(http.Handler) http.Handler` returning RFC 9457 429s, and mount it in cmd/api/main.go ahead of the auth routes. Have the scaffolder emit it for any route that hashes or verifies a password.
- **Test contradiction:** `TestRateLimiter_FailOpenWhenNoRedis` proves one `Allow` call returns true with a nil client. It says nothing about whether anything calls `Allow`; wiring gaps are invisible to unit tests of the unwired component.

[IMPORTANT] [SECURITY] internal/platform/auth/principal.go:23 — The `"superadmin"` wildcard is an unconstrained free-text value that disables tenant isolation, duplicated as a bare literal in two functions.
- **Issue:** `HasTenantAccess` returns true for any target tenant and `HasRole` returns true for any role when `p.Role == "superadmin"`. The literal is not a constant, is not defined in the domain `Role` enum (internal/modules/auth/entity.go:12-13 declares only `admin` and `member`), and the backing column is `role VARCHAR(32) NOT NULL DEFAULT 'member'` (sql/migrations/0001_init.sql:17) with no `CHECK` constraint. The role is then copied into the JWT (token.go:46) and trusted for the token's whole lifetime.
- **Failure scenario:** Two paths. (1) A downstream module scaffolded with an update handler binds `role` from the request body (the generated handler pattern binds body fields straight into the DTO); a tenant-A admin sets their own role to `superadmin`, gets a new token, and reads and writes every tenant in the system while `tenant.Middleware` happily approves any `X-Tenant-ID`. (2) A genuine superadmin is demoted in the database; because the grant lives in an already-issued JWT with a 24 hour TTL and nothing calls `RevokeToken`, they keep global cross-tenant access for up to 24 hours after the demotion commits.
- **Suggestion:** Define the value once as an exported constant in `platform/auth`, add a `CHECK (role IN (...))` constraint on the column, and require a fresh authorization lookup (or a short-TTL token plus mandatory revocation on role change) rather than trusting a long-lived claim for the single most powerful grant in the system.
- **Test contradiction:** `TestAuthPrincipal_Methods` (auth_test.go:34-35) asserts `superadmin.HasTenantAccess("any-tenant")` and `HasRole("any-role")` are both true. That test pins the wildcard as intended behavior; it does not evaluate whether the grant is constrained at its source, nor the staleness window between demotion and token expiry.

[IMPORTANT] [SECURITY] internal/platform/auth/token.go:73 — The revocation check fails open on any Redis error, and the error is discarded.
- **Issue:** `revoked, err := s.IsTokenRevoked(ctx, jti); if err == nil && revoked { return nil, ErrTokenRevoked }`. When `err != nil` the condition short-circuits and validation continues as if the token were clean. The error is never logged, never surfaced to the caller, and never counted.
- **Failure scenario:** Redis fails over (a few seconds of `ECONNREFUSED`, or the request context hits its deadline mid-`EXISTS`). Every revoked token in the blocklist, including one revoked 10 seconds earlier for a confirmed compromise, is accepted for the duration of the outage. Operators see zero signal because the branch is silent.
- **Suggestion:** Make the policy explicit and configurable: a `FailClosed bool` on `TokenService` defaulting to closed for a security control, and at minimum log at Warn plus increment a counter on the error path so the fail-open window is observable.

[IMPORTANT] [BUG] internal/platform/security/argon2id.go:75 — `VerifyPassword` trusts the cost parameters and key length decoded from the stored hash without any bounds check.
- **Issue:** `m`, `t`, `p` are `Sscanf`'d from the encoded string and fed straight into `argon2.IDKey`, and `params.KeyLength = uint32(len(hash))` is taken from the decoded tail. `golang.org/x/crypto/argon2` panics on `time < 1` and on `threads < 1` (argon2.go:107,110), and `extractKey` with `keyLen == 0` calls `blake2b.New(0, nil)`, which returns a typed-nil digest whose error is discarded, so the next `Write` panics with a nil-pointer dereference. Memory is allocated as requested with no ceiling.
- **Failure scenario:** A downstream team imports legacy users from another system that emitted `$argon2id$v=19$m=1048576,t=3,p=4$<salt>$<hash>` (1 GiB). Every login attempt for those accounts allocates 1 GiB; a handful of concurrent attempts OOM-kills the pod. A truncated import row ending in `$argon2id$v=19$m=65536,t=3,p=4$c29tZXNhbHQ$` (six segments, empty hash) panics inside `VerifyPassword` on every login attempt for that account; chi's `Recoverer` converts it to a 500, so the account is permanently un-loggable-in with a misleading error and a stack trace in the logs.
- **Suggestion:** Validate after decoding: reject `Iterations < 1`, `Parallelism < 1`, `len(hash) < 16`, `len(salt) < 8`, and `Memory` above a configured ceiling (for example 4x the default), returning `ErrInvalidHash`. Never hand externally sourced cost parameters to a KDF unchecked.
- **Test contradiction:** `TestArgon2id_HashAndVerify` round-trips a hash produced by `HashPassword` in the same test, so every decoded parameter is well-formed by construction. No test feeds `VerifyPassword` a hostile or malformed encoded hash.

[IMPORTANT] [SECURITY] internal/platform/auth/token.go:27 — The signing key is accepted without validation, and there is no `kid` or rotation story despite the documented `jwk.Cache`.
- **Issue:** `NewTokenService(secret string, ...)` does `[]byte(secret)` with no minimum length and no empty check; HMAC accepts any key length, so `jwt.Sign` succeeds with a 0-byte key. Signing is a fixed `jwa.HS256` with no `kid` header (token.go:57), and stack-standards.md's promised `jwk.Cache` auto-rotation appears nowhere in the repo.
- **Failure scenario:** Two concrete outcomes. (1) `internal/config/config.go:50` gives `JWT_SECRET` the committed default `dev-super-secret-jwt-signing-key-32b`; a deployment that forgets the env var boots silently and anyone reading this public repo can mint a token with `role: "superadmin"` and own every tenant. `NewTokenService` is the last place that could reject it and does not. (2) With no `kid` and a single key, rotating `JWT_SECRET` invalidates every outstanding token at once, logging out the entire user base with no overlap window. Symmetric HS256 also means every service that *verifies* tokens can *mint* them.
- **Suggestion:** Return an error from `NewTokenService` for a secret shorter than 32 bytes and for the known dev default when not in a dev environment. For rotation, set a `kid` header at sign time and accept a keyset (current plus previous) at verify time; that is also the shape that later admits `jwk.Cache` and asymmetric keys.

[IMPORTANT] [SECURITY] internal/platform/auth/session.go:23 — A nil Redis client silently yields SCS's in-memory store rather than an error.
- **Issue:** `if rdb != nil { sessionManager.Store = goredisstore.New(rdb) }`. `scs.New()` defaults `Store` to `memstore.New()` (scs/v2 session.go:110), so the nil branch produces a working-looking session manager backed by per-process memory, and the constructor returns no error to signal it.
- **Failure scenario:** Same trigger as the token service: `REDIS_URL` is unset or malformed, `rdb` is nil, the app boots green. With 3 API replicas behind a round-robin load balancer, a user logs in on pod 1 and is anonymous on pods 2 and 3, so roughly two out of three requests appear logged out. Every deploy or restart logs everyone out. This also violates Rule 3's intent that session state never lands on a per-process or primary-database path. The `memstore` cleanup goroutine additionally runs forever with no tie-in to the Rule 13 shutdown coordinator.
- **Suggestion:** Change the signature to `(*scs.SessionManager, error)` and fail fast when `rdb == nil`; if an in-memory mode is genuinely wanted for tests, make it an explicit separate constructor.

[IMPORTANT] [DESIGN] internal/platform/security/rate_limiter.go:31 — The fail-open fallback is one process-global bucket that ignores both the key and the requested rate.
- **Issue:** `localLimiter` is a single `rate.NewLimiter(rate.Every(time.Second/100), 100)` created once per `RateLimiter` and shared by every call. The `key` and `rps` arguments are simply dropped on the fallback path, so per-IP, per-tenant, and per-endpoint isolation vanishes exactly when the system is already degraded.
- **Failure scenario:** Login is configured at 5 rps per IP and the search endpoint at 200 rps. Redis blips. (a) The attacker's brute force is now allowed at up to 100 rps instead of 5, a 20x increase in guesses during the outage. (b) Simultaneously, that single attacker drains the shared 100-token bucket, so every legitimate user at every other IP and every other endpoint gets `false` from `Allow`. The policy is fail-open for the abuser and fail-closed for everyone else, which is the inverse of the intent stated in Rule 12.
- **Suggestion:** Keep a small bounded LRU of per-key `*rate.Limiter` values constructed from the caller's `rps`, so the fallback preserves key isolation and the configured rate. Cap the map size to avoid unbounded growth under key cardinality attacks.
- **Test contradiction:** `TestRateLimiter_FailOpenWhenNoRedis` makes exactly one `Allow` call with one key and asserts true. It never makes a second call with a different key, never passes two different `rps` values, and never exhausts the 100-token burst, so neither the key collapse nor the ignored rate is observable.

[IMPORTANT] [BUG] internal/platform/auth/token.go:80 — Missing claims are coerced to the literal string `"<nil>"` instead of failing closed.
- **Issue:** `tenantID, _ := tok.Get("tenant_id")` discards the `ok` flag, then `fmt.Sprint(tenantID)` is applied to an `any` that is `nil` when the claim is absent. `fmt.Sprint(nil)` yields `"<nil>"`, so `principal.TenantID`, `Email`, and `Role` become the four-character string `"<nil>"` rather than empty or an error. Non-string claim types are likewise coerced instead of rejected.
- **Failure scenario:** Any token minted outside `GenerateToken` (a service-to-service token, a token from a previous schema version, a token issued before `tenant_id` was added) validates successfully and produces `TenantID == "<nil>"`. `tenant.Middleware` then sets that as the active tenant, and `RunInTx` executes `set_config('app.current_tenant_id', '<nil>', true)`; against a uuid-typed RLS predicate this raises `invalid input syntax for type uuid` and returns a 500 on every request from that principal, with a log line that makes it look like a database fault rather than a claims problem. The distinction between "no tenant" and "tenant literally named `<nil>`" is also erased for `HasTenantAccess`.
- **Suggestion:** Assert the type and presence explicitly: `s, ok := raw.(string); if !ok { return nil, ErrInvalidToken }` for each required claim, and treat a missing `sub` or `tenant_id` as a validation failure rather than a value to synthesize.

[IMPORTANT] [DESIGN] internal/platform/security/aes.go:19 — The ciphertext envelope carries no key identifier or associated data, so the key can never be rotated.
- **Issue:** The output is `base64(nonce || ciphertext)` with no version byte and no key id, and `gcm.Seal(..., nil)` passes no AAD. The function signature offers no way to bind a ciphertext to its row, column, or tenant, which is inconsistent with the sibling `EnvelopeEngine.Encrypt`, which does take `associatedData`.
- **Failure scenario:** An operator rotates the field encryption key after an incident. Every previously encrypted PII column now fails `gcm.Open` with an authentication error, and because nothing in the stored blob identifies which key produced it, there is no way to run dual-key decryption or a background re-encryption sweep. The only recovery is restoring the old key, which defeats the rotation. Separately, with no AAD, a ciphertext copied from tenant A's row into tenant B's row decrypts cleanly.
- **Suggestion:** Prefix the envelope with a version byte and a key id (`v1:<keyID>:<nonce||ct>`), resolve the key by id on decrypt, and add an `associatedData []byte` parameter bound to the tenant and column so a relocated blob fails authentication.
- **Test contradiction:** `TestAES256GCM_EncryptDecrypt` uses one key for both operations and only asserts that a *wrong* key fails. It never models rotation, which is the case where the missing key id is fatal.

[IMPORTANT] [CLARITY] internal/platform/auth/session.go:20 — Cookie policy is hardcoded with a magic number, cannot be configured, and sets no idle timeout.
- **Issue:** `sessionManager.Cookie.SameSite = 3 // http.SameSiteStrictMode` uses a raw integer with a comment that restates the constant it should have used; the field's type is `http.SameSite`, so `http.SameSiteStrictMode` compiles directly. `Secure = true` is likewise unconditional, and `IdleTimeout` is left at 0 (never idles out) against a 24 hour absolute `Lifetime`.
- **Failure scenario:** Three concrete breakages. (1) A developer runs the docker-compose stack over `http://localhost`; the browser drops the `Secure` cookie, so login appears to succeed and every subsequent request is anonymous, with no error anywhere to explain it. (2) A downstream team adds SSO; the IdP's top-level redirect back to the app does not carry a `SameSite=Strict` cookie, producing an infinite login loop that cannot be fixed without editing platform code. (3) With `IdleTimeout` at 0, an abandoned session on a shared machine stays valid for the full 24 hours.
- **Suggestion:** Use the named `http.SameSite*` constants, and accept a cookie policy struct (or the `config.Config`) so `Secure`, `SameSite`, `Domain`, and `IdleTimeout` are set per environment. A framework constructor named "production-ready" should not force one policy on all 50 downstream services.

[SUGGESTION] [PERF] internal/platform/security/rate_limiter.go:47 — One Warn log per request during a Redis outage, with no circuit breaker despite `platform/resilience` existing.
- **Issue:** Every failed `Allow` logs at Warn with the key attached. There is no sampling, no dedupe, and no breaker, even though `internal/platform/resilience` already provides `NewCircuitBreaker` per Rule 12.
- **Failure scenario:** At 2,000 rps, a 5-minute Redis outage emits ~600,000 Warn lines carrying rate-limit keys (often client IPs, which is PII in log storage), and each request still pays the full 100ms timeout before falling back, adding 100ms of latency to every request in the system.
- **Suggestion:** Wrap the Redis call in a `failsafe-go` circuit breaker so an open circuit short-circuits straight to the local limiter without the 100ms wait, and log the state transition once per open/close instead of once per request.

[SUGGESTION] [CLARITY] internal/platform/security/tink.go:34 — `Encrypt` and `Decrypt` accept a `context.Context` and discard it.
- **Issue:** Both methods take `ctx` and never reference it; the underlying `tink.AEAD` interface is synchronous.
- **Failure scenario:** A caller wraps `Decrypt` in `context.WithTimeout` expecting the KMS round trip implied by the type name `EnvelopeEngine` to be bounded. Once a real KMS-backed implementation lands, the parameter is still ignored unless someone remembers to thread it through, and the timeout silently does nothing in the meantime.
- **Suggestion:** Either drop the parameter until it is honored, or document on the method that it is reserved for the KMS-backed implementation. If a KMS constructor is added per the critical finding above, thread the context into the KMS client call.

[NITPICK] [BUG] internal/platform/auth/token.go:128 — The `Bearer ` scheme prefix is matched case-sensitively.
- **Issue:** `strings.HasPrefix(authHeader, "Bearer ")`. RFC 7235 defines the auth-scheme token as case-insensitive.
- **Failure scenario:** A client sending `Authorization: bearer eyJ...` (some HTTP libraries and hand-written curl invocations do) is treated as having presented no credentials at all, and because of the silent fall-through above, gets a confusing domain-level "unauthenticated" instead of a 401 pointing at the header.
- **Suggestion:** Split on the first space and compare the scheme with `strings.EqualFold`.

[NITPICK] [CLARITY] internal/platform/security/rate_limiter.go:37 — `Allow` declares an `error` return that is always nil.
- **Issue:** Every return path yields `nil` for the error, so the signature implies a failure mode callers cannot ever observe or handle.
- **Failure scenario:** A caller writes `allowed, err := limiter.Allow(...); if err != nil { return http.StatusServiceUnavailable }` believing they have opted out of fail-open, and that branch is dead code. The fail-open decision was already made inside the limiter.
- **Suggestion:** Either drop the error return, or return the underlying Redis error alongside the fallback verdict so callers can implement their own policy.

### Strengths
- `jwt.Parse` is called with `jwt.WithKey(jwa.HS256, ...)`, and jwx v2 builds the verifier from that option rather than from the token's `alg` header (jws.go:423-431), so the classic `alg: none` and HMAC/RSA confusion attacks are structurally impossible here. Passing the algorithm explicitly rather than deriving it from the token is exactly right and worth preserving as the copied pattern.
- The AES-256-GCM implementation is textbook: a fresh 12-byte nonce from `crypto/rand` per call via `io.ReadFull`, the nonce prepended through `gcm.Seal(nonce, nonce, ...)`, a key-size check before `NewCipher`, and a length check before slicing the nonce off on the decrypt side. No nonce reuse and no panic-on-short-input.
- Argon2id defaults (m=64 MiB, t=3, p=4, 16-byte salt, 32-byte key) match RFC 9106's second recommended configuration exactly, the salt comes from `crypto/rand` per hash, the encoding is the standard PHC string so hashes stay portable, and comparison goes through `subtle.ConstantTimeCompare`.
- `PrincipalFromContext` uses an unexported empty-struct key type, and both `HasTenantAccess` and `HasRole` nil-guard the receiver so a missing principal denies rather than panics. Small detail, but it is the one that keeps 50 copies of `principal.HasRole(...)` from becoming 50 nil dereferences.

### Out-of-slice observations
- internal/platform/tenant/middleware.go:19 trusts `X-Tenant-ID` unconditionally when `principal == nil`, which is the second half of the CRITICAL auth bypass above; the guard should be inverted to deny when no principal is present.
- internal/platform/router/router.go:32-37 sets `AllowedOrigins: ["https://*", "http://*"]` together with `AllowCredentials: true`, which reflects any origin on a credentialed CORS policy.
- internal/config/config.go:50 ships a committed `JWT_SECRET` default (`dev-super-secret-jwt-signing-key-32b`) that a deployment can silently inherit.
- cmd/api/main.go:65-71 discards the `redis.ParseURL` error, so a malformed `REDIS_URL` disables revocation, sessions, and distributed rate limiting with no log line.
- cmd/clericot/main.go:325 makes every scaffolded module read `tenant_id` from the request body with no principal or `HasTenantAccess` check, so the auth gap is reproduced once per generated module.
- internal/modules/auth/service.go:107-123 returns early on an unknown email without running Argon2id, creating a multi-hundred-millisecond timing oracle for user enumeration; a dummy verify against a fixed hash would close it.
- `NewSessionManager` has no callers, and no CSRF middleware exists anywhere, so the "hybrid" JWT-plus-cookie authentication and the CSRF protection claimed in stack-standards.md are only half built.
- `TestAuthPrincipal_Methods` asserts the superadmin wildcard is correct rather than testing a boundary, which pins the escalation surface in place; `TestArgon2id_HashAndVerify` only round-trips self-generated hashes; `TestRateLimiter_FailOpenWhenNoRedis` exercises a single call on a single key. These are the three tests whose shape hides the findings above.
