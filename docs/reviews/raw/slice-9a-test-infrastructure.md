## Slice 9a: Test infrastructure
**Files reviewed:** 3 | **Findings:** 1 critical, 6 important, 5 suggestion, 2 nitpick

### Findings

**[CRITICAL] [DRIFT] tests/testsuite/suite.go:244,266 — `SeedTenant`/`SeedUser` write through `SharedAdminPool`, so every seeded row is committed and `RunTestInTx` can never roll it back.**
- **Issue:** Both seeders accept a `ctx` but ignore any transaction bound in it (`sqlcgen.New(SharedAdminPool)` at lines 250 and 273). `SharedAdminPool` is a separate pool with autocommit semantics, so seeded `tenants`/`users` rows are durable for the entire package run. Rule 14 promises "Zero-State Test Isolation" and the function signature (`ctx context.Context`) actively signals that the call participates in the caller's transaction. It does not. The seeders also take no `*testing.T`, so they cannot register a `t.Cleanup` to compensate. Note this is not forced by RLS: `tenants` has no RLS policy at all and `app_user` holds INSERT on it (sql/migrations/0001_init.sql, 0002_rls.sql), so `SeedTenant` could run inside the test tx, and `SeedUser` could too whenever the seeded tenant matches the session tenant.
- **Failure scenario:** A downstream package seeds one shared tenant at package scope, then two tests each do `RunTestInTx(t, tid, func(ctx){ SeedUser(ctx, tid, "admin@acme.test", ...) })`, both believing the row is rolled back. The second test fails with `duplicate key value violates unique constraint "uq_tenant_user_email"`. Running that test alone passes; running the package fails; reordering changes which test fails. Unconditionally true today: any assertion of the form `SELECT count(*) FROM users` inside `RunTestInTx` counts rows left behind by every earlier test in the package.
- **Suggestion:** Resolve the executor from context first (fall back to `SharedAdminPool` only when no tx is present), and add explicit admin-scoped variants (`SeedUserAsAdmin`) for the cross-tenant negative-test case that RLS `WITH CHECK` genuinely blocks. Give the seeders a `*testing.T` so the admin-pool path can register `t.Cleanup` deleting the tenant (FK `ON DELETE CASCADE` handles users/orders).
- **Test contradiction:** `TestRunTestInTx_AutoRollback` (suite_test.go:22) appears to prove rollback, but it only proves it for the user row it creates *through the tx-bound `SharedTxManager.GetDB(txCtx)`*. The tenant it seeds on line 25 via `SeedTenant` is never asserted on and stays in the database forever. `TestRunTestInTx_TenantIsolation` likewise leaks 2 tenants and 2 users permanently. Both tests pass because every `SeedTenant` call mints a fresh random `tenant-<8 hex>` ID, so accumulated rows never collide within a single run.

**[IMPORTANT] [SECURITY] tests/testsuite/suite.go:103 — the app-pool connection string is derived by positional string replace with no verification that the resulting role actually lacks RLS bypass.**
- **Issue:** `strings.Replace(adminConnStr, "postgres:postgrespassword", "app_user:app_user_password", 1)` couples four literals that live in three places: `postgres.WithUsername`/`WithPassword` (lines 52-53), the `CREATE ROLE app_user WITH LOGIN PASSWORD 'app_user_password'` in sql/migrations/0002_rls.sql, and this line. If the substring does not match, `strings.Replace` returns the input unchanged — no error — and `SharedAppPool` silently becomes a second superuser pool. distilled-lessons §1 states that superusers silently bypass `FORCE ROW LEVEL SECURITY`; nothing in bootstrap asserts `current_user = 'app_user'` or `NOT rolsuper/rolbypassrls`.
- **Failure scenario:** A downstream team hardens the fixture and changes `postgres.WithPassword("postgrespassword")` to a generated value (or renames the container user to satisfy a secret scanner). The replace becomes a no-op, `database.NewPool` connects and pings successfully as `postgres`, bootstrap prints nothing, and every `RunTestInTx` in `internal/modules/*`, `internal/platform/*` and `cmd/api` now runs with RLS fully bypassed. Tenant-scoped repository tests still pass because they filter by `tenant_id` in the query itself; the RLS layer they are supposed to be validating is inert.
- **Suggestion:** Build the app URL by parsing the admin URL (`url.Parse` + `u.User = url.UserPassword(...)`) rather than substring surgery, and add a hard assertion right after `SharedAppPool` is created: `SELECT current_user, rolsuper, rolbypassrls FROM pg_roles WHERE rolname = current_user` must yield `app_user, false, false`, otherwise fail bootstrap. Source the app_user password from one shared constant used by both the migration and the suite.
- **Test contradiction:** `TestRunTestInTx_TenantIsolation` (suite_test.go:66) would catch this specific no-op-replace case, because a superuser session would see `userB` and `assert.NotContains` would fail. But that is one test, in one of seven packages that call `testsuite.Main`, covering one table (`users`). The other six packages would keep passing green with RLS disabled, and a downstream template consumer who trims or rewrites `tests/testsuite/suite_test.go` (an entirely normal thing to do with a scaffolded template) loses the only detector.

**[IMPORTANT] [DRIFT] tests/testsuite/suite.go:166 — `SharedRedis` is a package-wide singleton with no per-test reset, so Redis is the one shared dependency `RunTestInTx` does not isolate.**
- **Issue:** The Postgres side gets transaction rollback; Redis gets nothing. `SharedRedis` is created once on DB 0 and handed to every test; neither `RunTestInTx` nor `RunTestInSchema` flushes it, and there is no `t.Cleanup`, key-prefix namespacing, or per-test `SELECT <n>` database switch. Every Redis-backed subsystem in the stack (`SETEX auth:revoked:<jti>` revocation blocklists, Watermill `SET NX` idempotency guards, `redis_rate` GCRA counters, the L2 cache tier, SCS sessions, Asynq unique keys) is exactly the kind of cross-test-visible state Rule 14 says must be zero.
- **Failure scenario:** A downstream test asserts that a consumer processes event `evt-1` on first delivery (`SET NX audit:evt-1` succeeds). A later test in the same package asserts the retry path for the same event ID and expects `SET NX` to fail — it passes, but only because the earlier test left the key behind, not because the guard works. Invert the order (or run either test with `-run`) and the result flips. Equivalently: a rate-limiter test that expects the 6th request in a window to be rejected passes or fails depending on how many requests earlier tests already charged to the same GCRA key.
- **Suggestion:** Add a `RunTestInRedis`-style helper (or fold it into `RunTestInTx`) that issues `FLUSHDB` in `t.Cleanup`, or hand each test a `*goredis.Client` pinned to its own logical DB index drawn from a pool. At minimum document loudly that `SharedRedis` is not isolated.
- **Test contradiction:** `TestSharedRedis_Operations` (suite_test.go:152) passes, but it only does a `SET`/`GET` round trip on a `uuid`-suffixed key. It proves the container is reachable; it makes no claim about isolation and would pass identically against a Redis instance polluted by a thousand prior tests.

**[IMPORTANT] [BUG] tests/testsuite/suite.go:49-68,127-144 — the container retry loops overwrite the container handle without terminating the previous attempt, and the terminal failure paths skip termination entirely.**
- **Issue:** `postgres.Run` in testcontainers-go v0.44.0 returns a **non-nil** `*PostgresContainer` alongside its error (verified in the module source: `if ctr != nil { c = &PostgresContainer{...} }; if err != nil { return c, ... }`). The loop at lines 49-64 discards that handle and reassigns `pgContainer` on the next iteration, so a container created by a failed attempt is never terminated. The terminal path at lines 65-68 calls `os.Exit(1)` with `pgContainer` non-nil and no `Terminate` at all — every other failure path in `Main` does terminate it, so this is an inconsistency, not a policy. The Redis loop at 127-137 has the identical overwrite bug, and its terminal path (138-144) terminates `pgContainer` but never `redisC`.
- **Failure scenario:** On a loaded CI agent the 30s `WithStartupTimeout` expires on attempts 1 and 2 and succeeds on attempt 3. Two orphaned `postgres:16-alpine` containers stay running per package; with 7 packages calling `testsuite.Main` that is up to 14 orphans in one `go test ./...`, each holding a random host port and ~100MB. If the wait strategy fails all 3 times, the process exits with a live container and no cleanup call at all.
- **Suggestion:** Inside each loop, on error, `if c != nil { _ = c.Terminate(ctx) }` before retrying, and add the same guard to the terminal `os.Exit(1)` paths (including `redisC`). Extract a small `terminate(ctx, ctrs...)` helper so no exit path can forget one.

**[IMPORTANT] [DRIFT] tests/testsuite/suite.go:217-241 — `RunTestInSchema` produces an empty, unmigrated schema that no commit-dependent test can actually use.**
- **Issue:** The doc comment and both architecture docs (stack-standards.md line 41, "ephemeral test schemas"; §2.7, "ephemeral schemas for commit-dependent tests") advertise this as the escape hatch for tests that need real commits. But the helper only issues `CREATE SCHEMA` + `GRANT`: no migrations are applied into the schema, `search_path` is never set on any connection, and the callback receives a bare `context.Background()` with no pooled connection or tx bound to it. The `AUTHORIZATION app_user` / `GRANT ALL ... TO app_user` ceremony is unexercised — the only caller in the repo (suite_test.go:120) uses `SharedAdminPool` with fully-qualified table names, so neither `app_user` nor RLS is involved.
- **Failure scenario:** A downstream engineer follows the documented guidance to test the River outbox (which requires a real `COMMIT` to be visible to the job runner). They call `RunTestInSchema`, get a schema name, and every query fails with `relation "river_job" does not exist`, because `users`, `orders`, `river_job` and all RLS policies live only in `public`. To make it work they must re-run the full Goose migration set into the schema themselves, at which point the helper has provided nothing but a `CREATE SCHEMA` statement. Meanwhile true commit-dependent tests against `public` are being written without any isolation.
- **Suggestion:** Either make it real (apply `database.MigrateUp` into the schema with `search_path` pinned on a dedicated connection, and hand the callback a `*pgxpool.Pool`/`DBTX` already scoped to it), or delete it and replace it with an explicitly truncating helper (`RunTestCommitted` with a `t.Cleanup` that `TRUNCATE ... RESTART IDENTITY CASCADE`s the affected tables). Do not leave a documented capability that does not work.

**[IMPORTANT] [DRIFT] tests/fixtures/factories.go:12-20,73,260,327 — the factories are advertised as deterministic but are not reproducible under any nondefault execution order, and are never fully deterministic at all.**
- **Issue:** Three separate problems. (a) `init()` seeds the process-global `gofakeit.GlobalFaker`; determinism therefore depends on a single global draw sequence, which is only stable if tests run serially in source order. `-shuffle=on` or any `t.Parallel()` reorders consumption and every generated value changes. (b) `ResetSeed` is exported and rewinds that same global sequence, so one test mutates the fixture stream of every concurrently running test. (c) `NewUser`, `NewTenant`, `NewOrder` and `NewOrderItem` all stamp `time.Now().UTC()`, so the entities are never byte-reproducible regardless of seed — which is precisely the nondeterminism the docs claim `gofakeit` seeding eliminates. `GlobalFaker` is created with `Locked: true`, so `-race` stays clean; the hazard is nondeterminism, not a data race, which is why it is invisible to the current baseline.
- **Failure scenario:** Combined with the CRITICAL finding above: a package has a test that calls `ResetSeed(42)` (the same constant `init()` uses) to get reproducible values, then a later test calls `fixtures.NewUser()` and passes the result to `SeedUser`, which commits it. The stream has been rewound, so `NewUser()` reproduces an ID already committed by an earlier test, and the insert fails with a primary-key violation that reproduces only in full-package runs. Separately, a downstream engineer adds `t.Parallel()` to two table-driven tests and a failure that printed `usr-3f2a91bc` becomes unreproducible under `-run` because the draw order changed.
- **Suggestion:** Drop the global seed. Give each factory call site an explicit `*gofakeit.Faker` (`gofakeit.New(seed)`), e.g. `fixtures.NewFactory(t)` deriving a seed from `t.Name()` so values are per-test stable, reproducible under shuffle, and safe under parallelism. Make the timestamps injectable with a fixed default (`WithUserCreatedAt` already exists; the default should be a constant, not `time.Now()`). If `ResetSeed` must stay, unexport it or scope it to a local faker.
- **Test contradiction:** `TestFactories_DeterministicSeeding` (fixtures_test.go:119) passes, but it proves only that `Seed(100)` twice in a row on the same goroutine, with no interleaving and with nothing else touching the global, yields the same email. It never runs in parallel, never asserts on the timestamp fields, and never checks reproducibility across process runs or under `-shuffle`. It is a test of `math/rand/v2`'s PCG, not of the harness's isolation properties.

**[IMPORTANT] [DESIGN] tests/testsuite/suite.go:44,182 — `Main` hard-exits, so callers cannot add teardown; the MinIO container both docs promise is absent and cannot be added safely.**
- **Issue:** `Main(m *testing.M)` never returns — it calls `os.Exit(code)` at line 182. Any `defer` a caller registers in its own `TestMain` before calling `testsuite.Main(m)` is silently dead code. Meanwhile stack-standards.md line 41 ("Singleton `TestMain` Postgres/Redis/MinIO test containers") and project-layout.md line 44 ("Postgres/Redis/MinIO testcontainers") both promise a MinIO container that `Main` never starts, so `internal/platform/storage` has no container-backed coverage at all. There is also no extension point (no options, no registered-cleanup slice) for a downstream user to add one.
- **Failure scenario:** A downstream team needs MinIO for `gocloud.dev/blob` tests and writes the obvious thing: `func TestMain(m *testing.M) { c := startMinIO(ctx); defer c.Terminate(ctx); testsuite.Main(m) }`. The deferred `Terminate` never executes because `testsuite.Main` exits the process, leaking a MinIO container on every single `go test` invocation for that package. Same root cause: if any test in the package panics, `tRunner` re-panics and the process dies without ever reaching the cleanup block at lines 170-181, leaking both containers (Ryuk usually reaps these, but only when it has not been disabled).
- **Suggestion:** Split into `Setup(ctx) (teardown func(), err error)` and a thin `Main(m)` wrapper, or accept variadic options plus a `RegisterCleanup(func())` so callers can attach resources to the same lifecycle. Either reconcile the docs with reality (drop MinIO from both rows) or add the container behind an opt-in option so packages that do not need it do not pay for it.

**[SUGGESTION] [DRIFT] tests/testsuite/suite.go:128-131 — the custom Redis wait strategy replaces the module default and drops the listening-port check, and `SharedRedis` is never pinged.**
- **Issue:** The redis module's own default is `wait.ForAll(wait.ForListeningPort(redisPort).WithStartupTimeout(10s), wait.ForLog("* Ready to accept connections"))` (verified in modules/redis v0.44.0). Passing `testcontainers.WithWaitStrategy(wait.ForLog(...))` overwrites `WaitingFor` wholesale, so the socket-bind check is discarded and only the log line remains. distilled-lessons §4 says verbatim that log readiness does not guarantee socket bind. Postgres is protected from this by `database.NewPool`'s internal 10-attempt ping loop; Redis has no equivalent — `goredis.NewClient` at line 166 connects lazily and is never pinged.
- **Failure scenario:** On a contended CI host, `Main` returns with a `SharedRedis` pointing at a port that is not yet accepting connections. go-redis' default 3 dial retries usually paper over it, but when they do not, the first Redis operation in some unrelated test returns `dial tcp: connection refused` and gets triaged as a bug in that test rather than as a bootstrap race.
- **Suggestion:** Either drop the `WithWaitStrategy` override entirely (the module default is already stricter) or include `wait.ForListeningPort("6379/tcp")` in it, and add `SharedRedis.Ping(ctx)` with a short retry immediately after line 166 so a broken Redis fails bootstrap loudly.

**[SUGGESTION] [CLARITY] tests/testsuite/suite.go:77-88,104-115 — the outer pool retry loops duplicate retry logic that `database.NewPool` already performs, delaying credential errors by over a minute.**
- **Issue:** `database.NewPool` already retries `Ping` 10 times with a 2s timeout and 500ms backoff (~25s worst case) and returns `nil` on failure, so no pool is leaked. Wrapping it in a 3-attempt loop with a 1s sleep adds nothing for transient failures and actively harms permanent ones: `pgxpool.ParseConfig` errors and authentication failures are non-retryable but get retried anyway.
- **Failure scenario:** A downstream user mistypes the app_user password in migration 0002. The suite spends ~77 seconds (3 × 25s pings + 2s sleeps) before finally printing `failed to initialize app pool`. Multiply by 7 packages under `go test ./...`.
- **Suggestion:** Drop the outer loops and call `database.NewPool` once, or move the retry policy entirely into the suite and out of `NewPool` — but not both.

**[SUGGESTION] [PERF] tests/testsuite/suite.go:44 — every package pays a full Postgres + Redis container bootstrap, including six packages that never touch Redis.**
- **Issue:** Seven packages call `testsuite.Main` (`cmd/api`, `internal/modules/auth`, `internal/modules/orders`, `internal/platform/database`, `internal/platform/tenant`, `pkg/testharness`, `tests/testsuite`). Each gets its own Postgres container, its own full Goose migration run, and its own Redis container, unconditionally. `SharedRedis` is referenced by exactly one test in one package (suite_test.go:152); the other six pay the Redis pull, start, and wait for nothing. stack-standards.md §2.7 calls this the "High-Performance Testcontainers" tier with "migrations once" — it is once *per package*, not once per run.
- **Failure scenario:** At the observed ~35s per package, `go test ./...` spends roughly 4 minutes in container bootstrap before running a single assertion, and the cost scales linearly as downstream teams scaffold modules — the `make:module` path in cmd/clericot encourages exactly that growth.
- **Suggestion:** Gate the Redis container behind an option so only packages that ask for it start one. For the bigger win, support attaching to an externally provisioned container (env var override for the connection string, with the container path as fallback), or use `postgres.WithSnapshot`/`Restore` so migrations run once and each package restores instead of re-migrating.

**[SUGGESTION] [DESIGN] tests/testsuite/suite.go:188-215 — `RunTestInTx` rolls back when the callback returns, with no guard against callbacks that register parallel subtests or spawn goroutines.**
- **Issue:** The rollback is a plain `defer` in the runner. Rule 5 states "never share transaction contexts across goroutines," but the harness that hands out those contexts does not enforce or document it, and `pgx.Tx` is not goroutine-safe.
- **Failure scenario:** A test written as `RunTestInTx(t, tid, func(ctx){ for _, tc := range cases { t.Run(tc.name, func(t *testing.T){ t.Parallel(); ... use ctx ... }) } })` — a very common table-driven shape. The parent callback returns immediately, the deferred rollback fires, and the parallel subtests then run against a closed transaction, failing with `conn busy` or `tx is closed` in a way that looks like a database problem rather than a harness misuse.
- **Suggestion:** Document the constraint on the exported function, and detect the common case at runtime — capture whether the callback returned before its subtests by rolling back from `t.Cleanup` instead of `defer` (Cleanup runs after parallel subtests complete), which fixes the footgun rather than only warning about it.

**[NITPICK] [CLARITY] tests/testsuite/suite.go:225,231,232 — dead sanitization, a redundant GRANT, and a schema leak on the GRANT failure path.**
- **Issue:** `strings.ReplaceAll(uuid.NewString()[:8], "-", "")` can never remove anything: a UUID's first dash sits at index 8, so `[:8]` is always 8 hex characters. (Worth stating explicitly, since the review question raised injection: the `fmt.Sprintf` at 228/231/237 has **no** injection surface today for exactly this reason — the name is `test_schema_` plus 8 hex chars.) `GRANT ALL ON SCHEMA %s TO app_user` at line 231 is redundant after `CREATE SCHEMA ... AUTHORIZATION app_user`, which already makes `app_user` the owner. And the `defer` that drops the schema is registered only after both `require.NoError` calls, so if the GRANT fails the already-created schema is never dropped and persists in the shared container for the rest of the package run.
- **Failure scenario:** Low impact — a leaked empty schema, and a misleading suggestion to downstream readers that `fmt.Sprintf` into DDL is a pattern to copy for identifiers they do control.
- **Suggestion:** Drop the `ReplaceAll` and the redundant GRANT; move the `defer` to immediately after `CREATE SCHEMA` succeeds; use `pgx.Identifier{schemaName}.Sanitize()` so the pattern is safe to copy.

**[NITPICK] [DRIFT] pkg/testharness/harness.go:1,33,44 — a deprecated-on-arrival shim, outside the documented layout, whose only consumer is its own test and whose `Close` does not do what it says.**
- **Issue:** `pkg/` does not exist anywhere in project-layout.md's directory tree, yet this file is in the template's most public namespace and is marked `Deprecated:` in the same commit that introduced it. Its only importer is `pkg/testharness/harness_test.go`, which spins up a Postgres and a Redis container (~35s) to exercise 60 lines of pass-through delegation. `Close()` is documented as "terminates containers and pools" but `cleanupFn` is `func() {}` — harmless today, but it invites a downstream contributor to "implement" it, which would close the package-wide shared pools mid-run and break every other test. Line 33 also bakes a literal `"test-jwt-secret-key-32-characters-long"` into the exported `pkg/` surface, and passes `nil` for the Redis client so `TokenSvc` silently exercises none of the JTI revocation-blocklist path described in Rule 11.
- **Failure scenario:** A downstream team greps `pkg/` for the public API of the template, adopts `testharness.New(t)` as the sanctioned entry point (it is the only thing in `pkg/`), and inherits the deprecated path plus a `TokenService` whose revocation checks are permanently disabled.
- **Suggestion:** Delete the package. If a compatibility shim is genuinely needed, move it under `tests/` where the layout doc puts test infrastructure, fix the `Close` comment to say it is a no-op, and either wire a real Redis client into `NewTokenService` or document that revocation is not covered.

### Strengths
- The dual-pool split is the right shape: migrations and administrative DDL run as `postgres` while `SharedTxManager` is built over the unprivileged `app_user` pool, which is exactly what distilled-lessons §1 demands — the RLS layer is genuinely exercised rather than bypassed, and `TestRunTestInTx_TenantIsolation` proves it end to end.
- `RunTestInTx` correctly delegates tenant scoping to `tenant.SetTenantSession`, which uses parameterized `set_config('app.current_tenant_id', $1, true)` with `is_local=true`, so the setting is reverted by the transaction boundary and cannot contaminate a pooled connection reused by the next test. The rollback also uses a detached `context.Background()` with a 2s timeout, so a cancelled test context cannot strand a connection.
- Binding the transaction into the context via `database.WithTx` composes correctly with `TxManager.RunInTx`: production code under test transparently gets a `SAVEPOINT` pseudo-nested transaction rather than a second root transaction, so the code path exercised in tests is the real one.
- The functional-option factory shape (`WithUserEmail`, `WithOrderItems`) is clean, allocation-light, and reflection-free, and `WithOrderItems` correctly recomputes `TotalCents` from the items so callers cannot construct an internally inconsistent aggregate.

### Out-of-slice observations
- `internal/modules/auth/auth_test.go` never calls `RunTestInTx` at all — `Service.Register` commits real users to the shared database, so that package's rows accumulate with zero isolation.
- `cmd/api/api_test.go:38` and `internal/modules/auth/auth_test.go:27` each hardcode a distinct 32-character JWT secret literal, duplicating the one in `pkg/testharness/harness.go:33`; three different test secrets for one framework.
- `sql/migrations/0001_init.sql` leaves `tenants` with no RLS policy while granting `app_user` full DML on it, so any tenant-scoped session can read and modify every tenant row in the database.
- `internal/platform/cache/cache_test.go:19` constructs the engine with `NewCacheEngine(nil)` (L1-only), so the L2 Redis tier, singleflight, and Pub/Sub invalidation of Rule 10 have no coverage despite the harness already providing a Redis container.
- `cmd/clericot/main.go` scaffolds 6 module files (entity/repository/service/handler/worker/module) but emits no `*_test.go`, so every downstream module starts with zero wiring to this harness — the isolation guarantees are inherited by copy, not by scaffold.
- `internal/platform/tenant` has two test files (`tenant_test.go`, `worker_test.go`) in one package sharing a single `testsuite.Main`, which is the correct pattern and worth pointing at as the reference example.
