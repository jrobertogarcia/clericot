## Slice 7a: Cache & storage

### Findings

[CRITICAL] [SECURITY] internal/platform/storage/storage.go:49 — Client-supplied `filename` is joined into the object key unsanitized, so `..` segments escape the tenant prefix.
- **Issue:** `path.Join("tenants", tenantID, "uploads", fmt.Sprintf("%s-%s", uuid.NewString(), filename))` calls `path.Clean` on the result. Any `../` inside `filename` pops the preceding segments, including the `<uuid>-` segment, `uploads`, `<tenantID>`, and finally `tenants`. The escaped key is then handed to `bucket.SignedURL(ctx, key, PUT)`, so the caller receives a signed URL authorizing a write to that arbitrary location.
- **Failure scenario:** Verified against `path.Join` directly. With `tenantID = "T1"`: `filename = "../../../../evil.pdf"` yields key `tenants/evil.pdf`; `filename = "../../../../../tenants/victim/uploads/pwned.pdf"` yields key `tenants/victim/uploads/pwned.pdf`; `filename = "../../../../../etc/x"` yields `etc/x` at the bucket root. A tenant that knows or guesses a victim's object key (keys leak through presigned-URL query strings, audit logs, and browser history) obtains a signed PUT that overwrites the victim's document with attacker content. The returned `key` also flows back to the caller for persistence, so the app records the poisoned path as its own.
- **Suggestion:** Sanitize before joining: `name := path.Base(path.Clean("/" + filename))`, reject `""`, `"."`, `"/"`, and any name containing a separator; then assert the final key with `strings.HasPrefix(key, "tenants/"+tenantID+"/")` and return an error if it does not hold. Apply the same normalization to `tenantID` since it originates from the `X-Tenant-ID` header.
- **Test contradiction:** `storage_test.go:25` only passes `"invoice.pdf"` and asserts the happy-path prefix. No traversal input is exercised, and `memblob` accepts any key, so nothing in the suite would fail.

[CRITICAL] [SECURITY] internal/platform/storage/storage.go:67 — Every key-accepting method (`PresignedDownload`, `ConfirmUpload`, `Read`, `Write`, `Delete`) skips the tenant-prefix check that `PresignedUpload` enforces.
- **Issue:** Rule 8 and stack-standards §1 promise "tenant-prefixed presigned URLs" and a two-step confirmation flow, but only the *write*-URL generator derives the prefix from context. `PresignedDownload(ctx, key, expiry)` signs whatever key it is given with no reference to `TenantExtractor(ctx)`. `ConfirmUpload` likewise only asks "does this object exist?", which is exactly the question an attacker wants answered, and returns `*blob.Attributes` (size, content type, mod time, ETag) for it. The engine therefore provides no tenant boundary on read, and the "confirm" step contributes no authorization value.
- **Failure scenario:** The intended downstream flow is: client PUTs to the presigned URL, then calls `POST /confirm` with the `key` it was given, then later requests a download URL for a stored key. Tenant B submits `tenants/A/uploads/<uuid>-payroll.pdf` to the confirm endpoint. `ConfirmUpload` succeeds, B's database row now points at A's object, and B's subsequent download request returns a valid signed GET for A's file. Full cross-tenant read of another customer's documents, with no RLS involved because blob storage has no equivalent of Rule 4's engine-level isolation. `Delete` gives the same primitive for destruction.
- **Suggestion:** Add one unexported guard, e.g. `func (s *StorageEngine) scoped(ctx context.Context, key string) error` that recomputes `tenants/<tenantID>/` from context and rejects any key outside it, and call it first in `PresignedDownload`, `ConfirmUpload`, `Read`, `Write`, and `Delete`. Keep an explicitly named escape hatch (`ReadUnscoped`) for the system/worker paths that legitimately need it, so the unsafe case is opt-in and greppable.
- **Test contradiction:** `storage_test.go:37-44` calls `ConfirmUpload`/`Read` with a key the same context just created, so the scoped and unscoped behaviors are indistinguishable. There is no second-tenant context in the test.

[CRITICAL] [SECURITY] internal/platform/cache/cache.go:57 — `TenantKey` silently degrades a missing tenant to a shared `global` namespace, merging unrelated tenants into one cache bucket.
- **Issue:** When `tenant.FromContext(ctx)` returns `""` the function substitutes the literal `"global"` and returns a well-formed key. A missing-tenant bug therefore does not fail; it produces a namespace that every tenant-less request on every pod shares. Two independent hazards follow: (a) any code path where the tenant middleware did not run collides with every other such path, and (b) `tenant_id` is `VARCHAR(64)` with no reserved-value check, so a customer provisioned with the id `global` reads and writes the fallback bucket directly.
- **Failure scenario:** The common cache idiom splits the tenant between the key and the query: `FetchOrCompute(engine, ctx, cache.TenantKey(ctx, "settings", "billing"), ttl, func() (*Settings, error) { return repo.Get(ctx, job.TenantID) })`. In an Asynq or River worker the tenant lives in the job payload, not the context (only `PurgeTenantWorker` remembers to call `WithTenant`). Tenant A's job caches its billing settings under `tenants:global:settings:billing`; tenant B's job for the same natural key gets an L1/L2 hit and receives A's data. Natural keys (`settings`, slugs, invoice numbers, emails) collide readily; UUID ids do not, which is why this is silent until a non-UUID domain appears.
- **Suggestion:** Fail closed. Either return `(string, error)` and have `FetchOrCompute` propagate the error, or make the fallback unshareable (e.g. include a per-process id so a tenant-less entry can never be read by another caller). Reserve and reject `"global"` as a tenant id at registration. `Key()` at line 66 already exists for the genuinely global case, so the fallback in `TenantKey` has no legitimate user.
- **Test contradiction:** `cache_test.go:73-81` asserts exactly this behavior (`"tenants:global:orders:ord_1"`), locking in the fallback as intended. The test documents the string format; it does not evaluate whether a shared bucket is a safe outcome, and it never has two tenants contend for one key.

[CRITICAL] [DRIFT] internal/platform/cache/cache.go:110 — The `IsEmpty` cache-penetration defense is never written; only read. The documented protection does not exist.
- **Issue:** `CachedEntry[T].IsEmpty` is checked on both the L1 (line 79) and L2 (line 95) read paths, but the only construction site is `entry := CachedEntry[T]{Value: data}` at line 110, which always leaves it `false`. Grepping the whole repo (including CLI scaffolding templates) finds no assignment of `IsEmpty = true`. The field is also unreachable through the public API: `FetchOrCompute` builds the envelope internally, and `compute` can only return `(T, error)` — an error short-circuits at line 106 and caches nothing. distilled-lessons §4 and stack-standards §2.6 both state that missing records are cached with `IsEmpty = true` specifically to prevent "thundering herd database crashes on non-existent keys," and Rule 3 makes protecting PostgreSQL a first-class constraint.
- **Failure scenario:** Handler does `FetchOrCompute(engine, ctx, cache.TenantKey(ctx,"orders",id), ttl, func() (*Order, error) { return repo.Get(ctx, id) })`, where `repo.Get` returns `domain.ErrNotFound` for unknown ids. An enumeration scan of `/v1/orders/{uuid}` at 5k rps: every id is distinct, so `singleflight` (which collapses only concurrent callers of the *same* key) never merges anything, nothing is ever stored, and 5k rps of index misses land on the primary database. This is precisely the scenario the envelope was introduced to stop.
- **Suggestion:** Give `FetchOrCompute` a sentinel contract — e.g. accept a `notFound func(error) bool` predicate (or export `cache.ErrEmpty`) so that when `compute` reports a legitimate absence the engine stores `CachedEntry[T]{IsEmpty: true}` under a short negative TTL (typically much shorter than `l2TTL`, e.g. 10-30s) and subsequent reads return `(zero, nil)` from the existing branches. Without this, delete `IsEmpty` and correct the two documents, because an inert defense is worse than a documented absence.

[IMPORTANT] [BUG] internal/platform/cache/cache.go:104 — The singleflight closure captures the first caller's `ctx`; its cancellation fails all waiters and suppresses the L2 write.
- **Issue:** `c.group.Do(key, func() ...)` runs in whichever goroutine arrived first, and the closure uses that goroutine's `ctx` for both `compute()` (which almost always closes over the same request context) and `c.l2.Set(ctx, ...)` at line 118. Waiters B..J block on a computation governed by a context they do not own. The `Set` error is additionally discarded with `_ =`, so the failure is invisible.
- **Failure scenario:** Under a burst, caller A triggers the compute; A's client disconnects (browser navigation, upstream proxy timeout) and `ctx` is canceled 5 ms in. `compute()` returns `context.Canceled`, which propagates to all nine concurrent waiters as a 500 even though every one of their contexts is alive. In the milder variant where compute finishes first, `c.l2.Set` is called with the already-canceled context and silently no-ops: L1 on this pod has the value, but L2 never does, so every other pod recomputes for the full TTL. Both effects amplify precisely during the load spike the mechanism exists to absorb.
- **Suggestion:** Perform the cache writes on a detached context (`context.WithoutCancel(ctx)` with a short timeout), matching the pattern Rule 5 already mandates for deferred rollbacks, and log/count the `Set` error instead of discarding it. Use `singleflight.DoChan` with a `select` on the caller's own `ctx.Done()` so a departing leader cannot fail the followers.

[IMPORTANT] [BUG] internal/platform/cache/cache.go:144 — A failed L2 `DEL` returns before publishing, so peer pods never hear the invalidation and keep serving the stale value from L2 for the full TTL.
- **Issue:** `if err := c.l2.Del(ctx, keys...).Err(); err != nil { return err }` short-circuits the `Publish` at line 157. Local L1 was already cleared at line 138, which makes the calling pod look correct and hides the problem from whoever triggered the write.
- **Failure scenario:** A user updates their profile; the write commits; `Invalidate` runs and the `DEL` times out on a Redis failover blip (a few hundred ms). No message is published. Peer pods' L1 copies expire after the 2-minute fallback, then repopulate from L2, which still holds the pre-update value with its original TTL (say 1 hour). The stale profile is served cluster-wide for an hour with no self-healing, and the only signal is an error return that most service code will log and move on from. The originating pod, having cleared its own L1, shows the correct value, which makes the report irreproducible for the on-call engineer.
- **Suggestion:** Publish regardless of the `DEL` outcome (best-effort broadcast is strictly better than none), aggregate both errors with `errors.Join`, and wrap the whole `Invalidate` in a short `failsafe-go` retry as Rule 12 prescribes for exactly this class of transient Redis failure.

[IMPORTANT] [BUG] internal/platform/cache/cache.go:126 — Waiters share one mutable value instance, while L1/L2 hits get private copies — the same key returns aliased or unaliased data depending on timing.
- **Issue:** The closure returns `data` (the live `T` from `compute`), and `singleflight` hands that identical `any` to every waiter, so `res.(T)` yields the same pointer/slice/map to all of them. The L1 and L2 paths, by contrast, `json.Unmarshal` fresh into a per-caller `entry`. The aliasing is therefore non-deterministic: it appears only on the cold-miss burst.
- **Failure scenario:** `FetchOrCompute[*Order]` is called concurrently by ten handlers on a cold key. All ten receive the same `*Order`. One handler redacts a field before serialization, another appends to `order.Items` for a computed view — a data race and cross-request corruption where request 1's response contains request 2's mutation. This is exactly the kind of defect that survives review in downstream copies because the happy path is single-caller.
- **Suggestion:** Return a decoded copy on the compute path too (unmarshal `encoded` back into a fresh `CachedEntry[T]` before returning), so all three paths have identical copy semantics. If the extra allocation is unacceptable, document immutability loudly on the exported function and constrain `T` to value types.
- **Test contradiction:** `cache_test.go:17-54` runs ten concurrent callers under `-race` but `T` is `string` — an immutable value — and no caller mutates its result, so no race can be reported.

[IMPORTANT] [DRIFT] internal/platform/cache/cache.go:149 — The invalidation payload carries no version, contradicting Rule 10's "versioned payloads" and leaving the stale-write race unresolvable.
- **Issue:** Rule 10 mandates "Redis Pub/Sub invalidation with versioned payloads." The published struct is `{node_id, keys}` only. Version/generation numbers are the standard mechanism for rejecting a cache write that was computed before an invalidation; without one the engine cannot distinguish a fresh write from a stale one. The same missing version also means the JSON envelope has no schema tag.
- **Failure scenario:** (a) Stale resurrection: pod B misses key K and reads value v1 from the database; pod A commits v2 and calls `Invalidate(K)`; B, still in its compute closure, then writes v1 into L2 and its own L1 *after* the invalidation has been processed everywhere. L2 now holds v1 for the full `l2TTL` and no further invalidation is coming. (b) Schema drift: `T` gains a field in a rolling deploy; old-format entries unmarshal successfully with the new field zeroed, so new pods serve structurally valid but semantically wrong data until the TTL rolls over, with no way to mass-invalidate by version.
- **Suggestion:** Add a monotonic `Version`/`Generation` to both `CachedEntry` and the pub/sub message, stamped from a Redis `INCR` per key (or a per-key generation counter checked before `SET`); reject writes whose generation is older than the last observed invalidation, and reject reads whose envelope version does not match the compiled-in schema version. If versioning is judged not worth the cost, amend Rule 10 rather than leaving code and spec divergent.

[IMPORTANT] [DESIGN] internal/platform/cache/cache.go:30 — L1's fixed 2-minute TTL overrides the caller's `l2TTL`, so a caller asking for 10-second freshness silently gets up to 2 minutes of staleness.
- **Issue:** `ExpiryWriting[string, []byte](2 * time.Minute)` is applied globally, and both L1 write sites (line 93 on an L2 hit, line 123 after compute) inherit it. The API's only freshness knob is `l2TTL`, but effective freshness is `max(l2TTL, 2m)` whenever `l2TTL < 2m`. Worse, the L2-hit path at line 93 stamps a *full* fresh 2 minutes onto an entry that may be one second from L2 expiry, so an entry can outlive its L2 TTL on every pod that reads it.
- **Failure scenario:** A feature-flag or quota lookup cached with `l2TTL = 15*time.Second` (a reasonable reading of the API). An operator disables a flag and calls `Invalidate`; a pod whose pub/sub connection just reconnected missed the message; that pod serves the enabled flag for a further 2 minutes rather than the 15 seconds the caller specified. Rule 10 describes 2 minutes as a *fallback* ceiling, not a floor.
- **Suggestion:** otter v2 supports per-entry expiry (`Cache.SetExpiresAfter(key, d)`, `otter.ExpiryWritingFunc`). Set the L1 entry to `min(l2TTL, 2*time.Minute)` after each `Set`, and on the L2-hit path use the key's remaining L2 TTL (`c.l2.TTL(ctx, key)`) rather than a full 2 minutes.

[IMPORTANT] [BUG] internal/platform/storage/storage.go:57 — `SignedURL` errors are swallowed and a fake `storage://` URL is returned with `err == nil`, masking every real signing failure.
- **Issue:** The fallback exists for drivers without signing support (`memblob`, `fileblob`), but the `if err != nil` catch is unconditional: expired or unavailable credentials, a KMS/SigV4 failure, a misconfigured region, or an out-of-range expiry all return `(fmt.Sprintf("storage://%s", key), key, nil)`. Nothing is logged. `PresignedDownload` (line 73) has the identical defect. This is the swallowed-exception anti-pattern in review checklist §4, in a function whose caller has no way to detect the substitution.
- **Failure scenario:** Production on S3 with `expiry = 14 * 24 * time.Hour` (a plausible "two-week share link"). SigV4 caps presigned URLs at 7 days, so the driver errors, and the API returns HTTP 200 with body `{"url":"storage://tenants/T1/uploads/…"}`. Every client upload fails with an unresolvable scheme, and the server-side logs are clean. The same happens on any transient IMDS credential-refresh failure, turning a retryable blip into a silent, unmonitorable outage of the upload path.
- **Suggestion:** Distinguish the cases: `if gcerrors.Code(err) == gcerrors.Unimplemented` → return the `storage://` placeholder (ideally only when the engine was constructed with an explicitly non-signing driver); otherwise wrap and return the error. Also clamp/validate `expiry` against a documented maximum before calling the driver.
- **Test contradiction:** `storage_test.go:18` opens `mem://`, and `memblob` never implements `SignedURL`, so the suite exercises *only* the fallback branch. `require.NotEmpty(t, signedURL)` passes on the string `storage://tenants/tenant-org-99/uploads/…`, which means the test asserts the failure path is non-empty rather than that signing works.

[IMPORTANT] [BUG] internal/platform/storage/storage.go:137 — Not-found tolerance in `DeletePrefix` matches on error *text* rather than `gcerrors.NotFound`, so it works on memblob and breaks on real drivers.
- **Issue:** `!strings.Contains(err.Error(), "not found")` is driver-specific string matching. Verified in gocloud.dev v0.46.0: `memblob` uses `errors.New("blob not found")` (matches), while `s3blob` maps codes `NoSuchKey`/`NotFound` (no lowercase "not found" with a space, so no match), `fileblob` surfaces the OS error "no such file or directory", and `gcsblob` surfaces "storage: object doesn't exist". The portable check `gcerrors.Code(err) == gcerrors.NotFound` is available and is what the driver layer already computes.
- **Failure scenario:** A GDPR purge (`tenant/worker.go:120` calls `DeletePrefix(ctx, "tenants/<id>/")`) is retried by Asynq while the first attempt is still draining, or the list snapshot includes a key concurrently deleted by a lifecycle rule. On `fileblob` or GCS the delete returns not-found, the string check fails to recognize it, `DeletePrefix` aborts mid-iteration and returns an error, phase 2 fails, and Asynq retries — hitting the same already-deleted key each time until the task is archived to the DLQ. The tenant is marked `status = 'deleted'` in phase 1 while their PII objects remain in the bucket indefinitely, which is a reportable failure of the erasure obligation the worker exists to satisfy.
- **Suggestion:** Replace the string match with `gcerrors.Code(err) == gcerrors.NotFound`. Separately, accumulate per-object failures and continue the iteration rather than aborting on the first error, so one poison key cannot block the rest of a purge.
- **Test contradiction:** Both `storage_test.go:48` and `tenant/worker_test.go:29` use `mem://`, whose message happens to contain the matched substring; neither test deletes an already-deleted key, so the branch is not exercised at all on any driver.

[IMPORTANT] [DRIFT] internal/platform/storage/storage.go:19 — `TenantExtractor` is a mutable exported global wired by an `init()` side effect, and its empty return routes objects into a `tenants/global/` bucket that the GDPR purge never reaches.
- **Issue:** Two problems in one mechanism. (a) Rule 15 mandates explicit constructor wiring "without magical reflection"; a package-level `var` reassigned from `tenant.init()` is exactly the implicit, order-dependent wiring that rule targets — it is writable by any package at any time, invisible at the construction site, and an unsynchronized write if anything reassigns it after startup. Note that `cache.go:14` solves the identical problem by importing `tenant` directly, so the codebase teaches two contradictory answers. (b) When the extractor returns `""` (worker context, a route mounted before `tenant.Middleware`, or an import graph where `tenant`'s `init` never ran because nothing imported it), line 46 substitutes `"global"` and the upload succeeds silently.
- **Failure scenario:** A binary that imports `storage` but not `tenant` — plausible for a dedicated media/upload worker — never runs the `init()` hook, so `TenantExtractor` remains the default stub returning `""`. *Every* upload from that process lands under `tenants/global/uploads/…`. Those objects are not under `tenants/<tenantID>/`, so `PurgeTenantWorker`'s `DeletePrefix(ctx, fmt.Sprintf("tenants/%s/", tenantID))` will never delete them: a customer exercises their right to erasure, the database is scrubbed, and their uploaded documents persist in the bucket forever with no record pointing at them.
- **Suggestion:** Pass the extractor into `NewStorageEngine`/`NewStorageEngineWithBucket` as a constructor parameter (defaulting to a function that returns an error, not `""`), matching Rule 15 and the project-layout §4 example. Make an empty tenant a hard error for tenant-scoped operations rather than a fallback bucket.

[SUGGESTION] [DESIGN] internal/platform/storage/storage.go:123 — `DeletePrefix` accepts any prefix, including `""`, with no shape guard on a mass-delete primitive.
- **Issue:** `List(&blob.ListOptions{Prefix: prefix})` with an empty string enumerates the entire bucket and the loop deletes every object. The only caller today constructs a safe prefix, but this is a framework API that downstream services will call with request-derived values.
- **Failure scenario:** A downstream admin endpoint exposes `POST /admin/purge {prefix}` or computes `DeletePrefix(ctx, "tenants/"+req.TenantID+"/")` without validating `req.TenantID`. An empty or whitespace value produces `""` or `"tenants//"`; the former destroys every object for every tenant in a single unrecoverable pass (no versioning assumption is documented anywhere).
- **Suggestion:** Reject `prefix == ""` and any prefix that does not end in `/`; consider requiring the `tenants/<id>/` shape outright and exposing the unrestricted form under a separate, obviously-dangerous name. Add an object-count cap or a dry-run mode for operator-invoked calls.

[SUGGESTION] [DRIFT] internal/platform/storage/storage.go:43 — Rule 8's "bucket lifecycle expiration rules" and the orphan-cleanup half of the two-step confirm flow have no implementation or documentation anywhere in the repo.
- **Issue:** Rule 8 pairs presigned URLs and `POST /confirm` with "bucket lifecycle expiration rules to prevent ... orphan storage bloat." The engine generates keys and confirms them but nothing reaps the gap: a client that obtains a presigned PUT, uploads, and never calls confirm leaves an object with no database row. There is no lifecycle configuration in `docker-compose.yml`, no infrastructure definition, and no note in the package. (`ConfirmUpload` also imposes no size or content-type ceiling on what it accepts, so an unbounded object can be adopted after the fact.)
- **Failure scenario:** A flaky mobile client uploads a 50 MB video, then loses connectivity before `POST /confirm`. The object is billed and stored forever, invisible to every application query. At scale this is the exact bloat Rule 8 names. Because the framework ships no reaper and no lifecycle config, each of the 50 downstream services inherits the same leak.
- **Suggestion:** Either add an `uploads/` lifecycle-expiration rule to the MinIO bootstrap plus a documented required rule for S3/GCS, or add a scheduled Asynq sweeper that deletes unconfirmed keys older than the presign expiry. Have `ConfirmUpload` validate `attrs.Size` and `attrs.ContentType` against caller-supplied limits so confirmation is a real gate.

[SUGGESTION] [DESIGN] internal/platform/cache/cache.go:174 — The invalidation bus is at-most-once with no resync on reconnect, and every decode failure across the file is silently ignored.
- **Issue:** `pubsub.Channel()` reconnects transparently but messages published during a disconnect are lost permanently; go-redis's default 100-message channel buffer also drops under a slow consumer. There is no resubscribe hook to flush L1 on reconnect. Separately, the three `err == nil` guards (lines 78, 91, 191) treat every decode failure as a miss with no log, metric, or key eviction.
- **Failure scenario:** A pod's Redis connection drops for 3 seconds during a failover; two invalidations are published in that window. The pod serves those two keys stale until the 2-minute L1 expiry — bounded, but invisible: no metric distinguishes "we missed an invalidation" from normal operation, so the staleness is undiagnosable from a support ticket. Likewise, a `T` whose JSON shape changed turns into a 100% miss rate and a permanent recompute storm with no signal.
- **Suggestion:** Flush L1 entirely on `pubsub` reconnect (detectable via `redis.Options.OnConnect` or by using `pubsub.Receive` and observing `*redis.Subscription`), and emit counters for `cache.decode_error`, `cache.invalidation.received/dropped`, and L1/L2 hit ratios. The 2-minute ceiling is the correct mitigation; it should be stated in a comment as the deliberate staleness bound so downstream users do not shorten it without understanding why it exists.

[SUGGESTION] [BUG] internal/platform/cache/cache.go:132 — `res.(T)` is an unchecked type assertion on a value shared across all callers of a key.
- **Issue:** The singleflight group is keyed by string only and is shared by every instantiation of the generic function. If two call sites use the same key string with different `T`, a waiter receives the leader's type and the assertion panics rather than erroring.
- **Failure scenario:** A refactor introduces `FetchOrCompute[OrderSummary](engine, ctx, cache.TenantKey(ctx,"orders",id), …)` in a list endpoint while the detail endpoint still uses `*Order` with the identical key. Under concurrency the detail handler's waiter panics with an interface-conversion error inside an HTTP goroutine. The panic is timing-dependent, so it will not reproduce in a single-threaded test.
- **Suggestion:** `val, ok := res.(T); if !ok { return zero, fmt.Errorf("cache: type mismatch for key %s", key) }`. Optionally namespace the singleflight key with the type name so distinct types cannot collide at all.

[NITPICK] [CLARITY] internal/platform/cache/cache.go:71 — `FetchOrCompute(c *CacheEngine, ctx context.Context, …)` puts `context.Context` second, against the near-universal Go convention of `ctx` first.
- **Issue:** The generic constraint forces a free function rather than a method (Go does not allow type parameters on methods), but that only requires `c` to be a parameter, not that it precede `ctx`. Linters that enforce `context.Context` as the first argument will flag every downstream call site.
- **Failure scenario:** No runtime failure; the cost is 50 scaffolded modules each carrying a call whose argument order reads backwards, plus recurring lint suppressions.

[NITPICK] [CLARITY] internal/platform/cache/cache.go:164 — `Close` does not wait for `listenInvalidations` to exit, and `Invalidate` with no keys produces a raw Redis argument error.
- **Issue:** `Close` cancels the context and returns immediately; the subscriber goroutine may still be mid-iteration when the process proceeds through the coordinator's remaining phase-5 teardown (`redisClient.Close()` is the very next statement), producing a spurious connection error in the shutdown logs. Separately, `Invalidate(ctx)` with an empty variadic issues `DEL` with zero arguments, which Redis rejects with "wrong number of arguments"; a caller invalidating a computed-but-empty key slice sees a confusing low-level error.
- **Failure scenario:** Cosmetic. Noisy shutdown logs that mimic a real failure, and a misleading error message for an empty-slice invalidation.
- **Suggestion:** Add a `done chan struct{}` closed by the listener and waited on in `Close` (Rule 13's deterministic-shutdown goal), and early-return `nil` from `Invalidate` when `len(keys) == 0`.

### Strengths
- The read path degrades correctly on infrastructure failure: an L2 error or decode failure at lines 89-100 falls through to compute rather than propagating, so a Redis outage becomes a latency event rather than an availability event, with L1 plus singleflight absorbing the load. This is the right fail-open posture for a cache and pairs well with Rule 12's philosophy.
- The `CachedEntry[T]` envelope is the correct shape for the problem: storing the raw encoded bytes in L1 (rather than a decoded value) lets the L2-hit path populate L1 with zero re-encoding, and keeps a single serialization format across both tiers.
- Self-invalidation suppression via `nodeID` (line 192) is a small detail that is easy to omit and expensive to debug when missing; getting it right here means the publishing pod does not pointlessly re-clear its own L1.
- `StorageEngine` is a genuinely thin, driver-agnostic wrapper with a clean testing seam (`NewStorageEngineWithBucket`), and the `gocloud.dev/blob` choice keeps S3/GCS/Azure/MinIO/local behind one interface exactly as Rule 8 and stack-standards §1 intend.

### Out-of-slice observations
- `internal/platform/cache/cache.go` imports `tenant` directly while `storage.go` uses an injection hook to dodge a cycle; the two packages should agree on one mechanism, and the divergence is worth resolving at the platform level rather than per-file.
- Every storage test (`storage_test.go`, `tenant/worker_test.go`) uses `mem://`, so presigning, driver-specific not-found semantics, and lifecycle behavior are entirely unexercised, despite stack-standards §1 listing MinIO testcontainers in the harness.
- `cache_test.go` runs exclusively in L1-only mode (`NewCacheEngine(nil)`), so the L2 path, the pub/sub invalidation bus, `listenInvalidations`, and cross-pod coherence have no coverage at all.
- `tenant/worker.go:83` runs the GDPR scrub in a transaction but performs the storage purge outside it; a phase-2 failure leaves the tenant marked deleted with objects intact, and the task's idempotency on retry depends on `DeletePrefix` being resumable.
- `tenant/middleware.go` permits a request with no principal and no `X-Tenant-ID` header to proceed with no tenant in context, which is the upstream source of the `"global"` fallback conditions in both files of this slice.
