## Slice 4: Domain: auth module
**Files reviewed:** 5 | **Findings:** 1 critical, 8 important, 7 suggestion, 2 nitpick

### Findings

[CRITICAL] [SECURITY] internal/modules/auth/service.go:47 — Unauthenticated `POST /v1/auth/register` takes `tenant_id` from the request body and uses it verbatim as the RLS scope, so knowing a tenant ID is sufficient to join that tenant.
- **Issue:** `Register` accepts `dto.TenantID` straight from the HTTP body (handler.go:74-79) and passes it to `tenant.WithTenant(ctx, dto.TenantID)`, which becomes the value of `app.current_tenant_id` for the transaction. Nothing verifies that the caller is entitled to that tenant: there is no invitation token, no email verification, no allowlist, and the route carries no authentication. The RLS policy in `0002_rls.sql` only checks `tenant_id = current_setting(...)` and that the tenant is active, so it faithfully authorizes whatever the attacker asked for. The user is then issued a live 24h JWT with `tenant_id` and `tenants` claims for that tenant.
- **Failure scenario:** A contractor offboarded from tenant `acme-prod` knows the tenant ID (it is returned in `/v1/auth/me`, embedded in every JWT, and passed around in support tickets). They `POST /v1/auth/register {"tenant_id":"acme-prod","email":"x@throwaway.com","password":"...","name":"x"}` from any IP. They receive a Bearer token whose principal has `TenantID=acme-prod`, which `tenant.Middleware` and every downstream module accept, giving full member-level read access to that tenant's rows (e.g. all of `orders`) through the RLS boundary that is supposed to contain them.
- **Suggestion:** Do not let an unauthenticated body field select the tenant. Split the flow: (a) a tenant-provisioning/signup path that creates the tenant and its first admin, and (b) an invite-redemption register that takes a single-use, server-issued invite token which resolves to the tenant server-side. At minimum, require an authenticated tenant-admin principal for registration into an existing tenant.
- **Test contradiction:** `auth_test.go:32-41` seeds a tenant with the admin pool and then registers into it, which is exactly the attacker's request shape. The test asserts the call succeeds, so it encodes the vulnerability as expected behavior rather than covering it.

[IMPORTANT] [BUG] internal/modules/auth/service.go:48 — The read-then-write duplicate check is not the real guard, and the constraint that is the real guard surfaces as HTTP 500.
- **Issue:** `GetUserByEmail` followed by `CreateUser` inside one READ COMMITTED transaction is a classic TOCTOU: neither statement takes a lock on a non-existent row. The actual guard is `uq_tenant_user_email`, but `repository.go:47` returns the raw `*pgconn.PgError` (SQLSTATE 23505) unwrapped, `service.go:66` propagates it, and `mapDomainError` (handler.go:160) has no case for it, so it falls to `httperr.Transform` → `500 An unexpected error occurred`.
- **Failure scenario:** A user double-clicks "Sign up", or a mobile client retries on a slow network. Two requests with the same `(tenant_id, email)` overlap: both pre-checks return `ErrUserNotFound`, the first `INSERT` commits, the second blocks then fails with 23505. The client gets a 500 (which retry logic and error budgets treat as a server fault) instead of the 409 the same input returns when the requests are serialized. Argon2 CPU/memory has already been spent on the losing request.
- **Suggestion:** Drop the pre-check entirely and make the constraint authoritative: in `repository.go`, inspect the error with `var pgErr *pgconn.PgError; errors.As(err, &pgErr) && pgErr.Code == "23505"` and return `ErrUserAlreadyExists`. This removes a query from the hot path and makes both the racing and serialized cases return 409.
- **Test contradiction:** `auth_test.go:50-55` asserts `ErrUserAlreadyExists` for a duplicate registration, but the two registrations are strictly sequential, so the in-transaction pre-check always fires and `CreateUser` is never reached. No test issues concurrent registrations, so the 23505 path has zero coverage.

[IMPORTANT] [BUG] internal/modules/auth/repository.go:47 — An unknown or suspended tenant on register returns 500; `ErrTenantNotFound` is never produced by any code path.
- **Issue:** `users.tenant_id` has an FK to `tenants(id)`, and the RLS `WITH CHECK` additionally requires `status = 'active'`. Both failures come back as raw driver errors (SQLSTATE 23503 and 42501) that the repository returns untranslated, so `mapDomainError` falls through to a 500. `ErrTenantNotFound` is declared at entity.go:65 and mapped at handler.go:154, but no production code ever returns it — the mapping is unreachable.
- **Failure scenario:** A client posts `{"tenant_id":"typo-tenant", ...}` to `/v1/auth/register`. Server pays the full Argon2 cost, then answers `500 An unexpected error occurred` with the actual cause discarded. Same for a legitimately suspended tenant: an admin sets `status='suspended'` to offboard a customer, and every subsequent registration or login for that tenant becomes an unexplained 500 spike on the dashboard rather than a clean 4xx.
- **Suggestion:** Classify Postgres error codes in `repository.go` (23503 → `ErrTenantNotFound`, 42501/RLS-violation → a dedicated `ErrTenantInactive` mapped to 403), or have `Service.Register` load the tenant first and return `ErrTenantNotFound`/`ErrTenantInactive` before hashing.

[IMPORTANT] [SECURITY] internal/modules/auth/service.go:105 — Login is a timing oracle for account existence: no password verification work happens when the user is absent.
- **Issue:** When `GetUserByEmail` returns `ErrUserNotFound`, `Login` returns `ErrInvalidCredentials` immediately. When the user exists, the request additionally runs `argon2.IDKey` at m=64MB, t=3, p=4 — on the order of 100ms and 64MB of allocation. The two paths return byte-identical 401 responses but differ by two orders of magnitude in latency.
- **Failure scenario:** An attacker with a list of 100k candidate emails and a known tenant ID posts each to `/v1/auth/login` with a junk password and records the response time. Sub-10ms responses are non-users; ~100ms+ responses are confirmed accounts, ready for credential stuffing or phishing. No rate limiter is in place (see below), and the signal is large enough to survive network jitter without statistical work.
- **Suggestion:** On the user-not-found branch, verify the supplied password against a package-level dummy Argon2id hash (computed once at init with the same params) and discard the result before returning `ErrInvalidCredentials`, so both branches perform identical work.

[IMPORTANT] [DRIFT] internal/modules/auth/handler.go:66 — Register and login are registered with no ingress rate limiting in front of Argon2id, violating Golden Rule 9.
- **Issue:** Rule 9 mandates "edge rate limiting in front of **Argon2id** password hashing" and Rule 12 specifies `redis_rate`. `security.RateLimiter` exists (`internal/platform/security/rate_limiter.go`) but is referenced only by its own unit test; no route in the application is throttled. Worse, `service.go:38` hashes the password *before* the duplicate check, so an attacker does not even need a valid tenant to force the work.
- **Failure scenario:** 200 concurrent `POST /v1/auth/register` requests with garbage bodies each allocate a 64MB Argon2 memory block simultaneously: ~12.8GB peak RSS. The pod hits its memory limit and is OOM-killed, taking down all traffic, not just auth. A single laptop can sustain this; the requests are unauthenticated and the responses do not need to be read.
- **Suggestion:** Wire `security.NewRateLimiter` as a per-IP + per-(tenant,email) middleware in front of the `/v1/auth/*` routes, and add a bounded semaphore around `security.HashPassword` so concurrent Argon2 executions cannot exceed a memory budget. As the reference module, `auth` is where downstream teams will look for this pattern.

[IMPORTANT] [DRIFT] internal/modules/auth/service.go:33 — `Register` stages neither the River outbox job nor the audit CloudEvent, leaving `worker.go` dead and authentication events unaudited.
- **Issue:** `worker.go` defines `UserRegisteredJobArgs` (`auth.user_registered.v1`) and `TypeUserWelcomeEmail`, but nothing in the repo ever inserts them — the `auth.Service` has no `*river.Client` field at all. `orders/service.go:110-137` does exactly this correctly (`riverClient.InsertTx` + `audit.StageAuditLog` inside `RunInTx`). Rule 9 requires audit CloudEvents staged atomically inside `RunInTx`; registration and login are the canonical SOC 2 auditable events and produce no trail whatsoever.
- **Failure scenario:** A downstream team scaffolds `billing` from this reference, ships, and during a SOC 2 audit is asked to produce the actor/IP/timestamp record for every account creation in tenant X. There is none: no audit row, no outbox event, and no log line (the module emits zero `slog` calls). Separately, no user ever receives a welcome email despite the worker being deployed and registered, and the failure is silent because there is no producer to fail.
- **Suggestion:** Add `riverClient *river.Client[pgx.Tx]` to `NewService`, and inside the `RunInTx` closure stage both `UserRegisteredJobArgs` via `InsertTx` and an `audit.AuditPayload{Action: "auth.register", ...}` via `audit.StageAuditLog`, mirroring `orders`. Do the same for a `auth.login.success`/`auth.login.failed` audit event.

[IMPORTANT] [BUG] internal/modules/auth/repository.go:59 — Email is never normalized, so case-variant addresses create duplicate accounts and lock users out.
- **Issue:** `uq_tenant_user_email` is over the raw `VARCHAR(255)` (not `citext`), `GetUserByEmail` does an exact `email = $1` match, and neither `Service.Register` nor `Service.Login` lowercases or trims. Email local parts are case-insensitive in every practical mail system.
- **Failure scenario:** A user registers as `Jane.Doe@Example.com` from a desktop browser that capitalizes, then logs in from a phone keyboard as `jane.doe@example.com`. `GetUserByEmail` returns no rows → `ErrInvalidCredentials` → 401 with a correct password, and the user is permanently locked out of an account they cannot see. Worse, that same address now registers successfully as a *second* distinct user in the same tenant, so a future "reset password by email" feature has two rows to choose from for one mailbox.
- **Suggestion:** Normalize once at the domain boundary (`strings.ToLower(strings.TrimSpace(dto.Email))` in a `RegisterDTO.Normalize()`/`Validate()` method in entity.go), applied in both `Register` and `Login`, and back it with a `citext` column or a `UNIQUE (tenant_id, lower(email))` index so existing rows cannot drift.
- **Test contradiction:** Fixtures use `gofakeit.Email()` (`tests/fixtures/factories.go:74`), which returns lowercase only, so every test email round-trips identically and the case-variance path is never entered.

[IMPORTANT] [DESIGN] internal/modules/auth/service.go:33 — All password and email invariants live in Huma struct tags; the service and entity enforce nothing.
- **Issue:** `minLength:"8"` and `format:"email"` exist only on `RegisterInput.Body` (handler.go:18-20). `Service.Register` validates only that `TenantID != ""`. project-layout.md assigns "validation methods" to `entity.go`, which has none. This makes the domain service unsafe to call from anywhere except the one HTTP handler, in a framework whose stated architecture has workers, seeders, and cross-module service calls.
- **Failure scenario:** A `db:seed` command or a bulk-import worker calls `Service.Register(ctx, RegisterDTO{TenantID: t, Email: row[0], Password: row[1]})` where `row[1]` is empty for rows the CSV omitted. Argon2 happily hashes the empty string; the accounts are created and are trivially compromised by anyone who tries an empty password against the login endpoint, which also does not validate. Nothing in the stack rejects it.
- **Suggestion:** Add `func (d RegisterDTO) Validate() error` and `func (d LoginDTO) Validate() error` to entity.go returning `ErrValidation`-style sentinels, call them at the top of `Register`/`Login`, and treat the Huma tags as documentation/fast-fail rather than as the enforcement point.

[IMPORTANT] [DRIFT] internal/modules/auth/handler.go:115 — `/v1/auth/me` declares no Huma `Security`, so the OpenAPI contract advertises it as public and there is no transport-level auth gate.
- **Issue:** Golden Rule 2 and stack-standards.md require Huma `SecuritySchemes` integration; `grep -rn "Security"` over the repo returns only comments. `TokenService.HTTPMiddleware` is deliberately non-blocking (token.go:130 — it attaches a principal on success and silently continues on failure), so the *only* thing protecting the endpoint is the `principal == nil` check hand-written at service.go:151.
- **Failure scenario:** A downstream team scaffolds a module from this reference and adds `GET /v1/invoices/{id}` whose service method reads the tenant from context but forgets the nil-principal check (or reads the tenant from a path param, as `Register` does from the body). The endpoint is fully public: no middleware rejects the request, no OpenAPI scheme flags it in review, and no generated client makes the omission visible. The 401 depends entirely on every author remembering an unenforced convention.
- **Suggestion:** Register a `bearer` HTTP security scheme on the Huma config and add `Security: []map[string][]string{{"bearer": {}}}` to the `get-current-user` operation, plus a Huma middleware that rejects requests for operations declaring a scheme when no principal is present. That makes the gate declarative and inherited by all 50 downstream copies. (The config-side scheme registration lives in `internal/platform/router`, outside this slice.)

[SUGGESTION] [SECURITY] internal/modules/auth/service.go:38 — `AUTH_ARGON2_*` configuration is silently ignored.
- **Issue:** `config.AuthConfig` exposes `Argon2MemoryMB`, `Argon2Time`, and `Argon2Threads` (config.go:53-55), but `Register` hardcodes `security.DefaultArgon2Params()`. `grep` confirms those fields are read by nothing except `config_test.go`.
- **Failure scenario:** In response to a hardening ticket, an operator sets `AUTH_ARGON2_MEMORY_MB=128` and `AUTH_ARGON2_TIME=4`, restarts, sees a green deploy, and closes the ticket. Hashing parameters are unchanged. The organization now believes it has remediated when it has not, and the discrepancy is invisible until someone reads the source.
- **Suggestion:** Pass an `*security.Argon2Params` built from config into `NewService` (constructor DI, per Rule 15) and use it in `HashPassword`; verification already reads params from the encoded hash, so existing hashes keep working.

[SUGGESTION] [DESIGN] internal/modules/auth/module.go:23 — The `if api != nil` branch is a test-only escape hatch that silently produces a module with no routes.
- **Issue:** project-layout.md's canonical `NewModule` has no such branch; it exists solely because `auth_test.go:29` calls `NewModule(nil, ...)`. It also does not do what it appears to: `huma.API` is an interface, so a typed-nil implementation (`var a *humachi.adapter; NewModule(a, ...)`) passes `api != nil` and panics inside `huma.Register`.
- **Failure scenario:** A future `cmd/api/main.go` refactor makes `bundle.API` conditional (e.g. only built when a flag is set) and passes nil on one path. The service starts, health probes report UP, and every auth request returns Huma's 404 — a config error that should have failed fast at boot instead becomes a silent, total outage of authentication. Replicated across 50 scaffolded modules, this is 50 silent-skip branches.
- **Suggestion:** Require a non-nil `api` and let tests construct the collaborators directly (`NewRepository`/`NewService`), or add an explicit `NewModuleWithoutRoutes` used only by tests. Production wiring should never have a "maybe register the routes" mode.

[SUGGESTION] [SECURITY] internal/modules/auth/handler.go:150 — Register returns a 409 whose body states the email is already registered, an account-enumeration oracle on an unauthenticated endpoint.
- **Issue:** `ErrUserAlreadyExists` → `409 "user with this email already exists"`. Combined with the absent rate limiting, this is a direct, single-request membership check.
- **Failure scenario:** An attacker enumerates which employees of a known tenant hold accounts by posting candidate corporate addresses to `/v1/auth/register` and reading the status code — 409 means "account exists". The harvested list feeds targeted phishing that references the real product, and the same accounts are then credential-stuffed at `/v1/auth/login`.
- **Suggestion:** For a public registration endpoint, return `202 Accepted` uniformly and deliver the outcome out of band (either "welcome" or "you already have an account") by email. If a synchronous 409 is a hard product requirement, gate it behind the invite-token flow from the CRITICAL finding, where the caller already proves tenant membership.

[SUGGESTION] [DRIFT] internal/modules/auth/service.go:83 — 24-hour token TTL is hardcoded and duplicated, and no endpoint ever populates the revocation blocklist.
- **Issue:** `expiry := 24 * time.Hour` appears identically at service.go:83 and service.go:133, is not in `AuthConfig`, and there is no refresh-token concept. Rule 11 mandates "JWX (with Redis revocation blocklists)"; `TokenService.RevokeToken` exists and is called by nothing — there is no logout operation in `RegisterRoutes`, so the JTI blocklist is permanently empty in production.
- **Failure scenario:** A user reports a stolen laptop with an active session. Operations has no lever: there is no logout endpoint, no password-change path that invalidates tokens, and no admin revoke. The only remedy is rotating `AUTH_JWT_SECRET`, which signs out every user in every tenant. The attacker retains full access for up to 24 hours regardless.
- **Suggestion:** Move the TTL to `AuthConfig` and inject it into `NewService`; add `POST /v1/auth/logout` that reads the JTI from the current principal and calls `RevokeToken` with the token's remaining TTL. Also return the expiry from `GenerateToken` rather than recomputing `time.Now().Add(expiry)` at service.go:91/141, which is a second, slightly later clock reading than the `exp` claim.

[SUGGESTION] [DESIGN] internal/modules/auth/repository.go:93 — `ListUsersByTenant` and `DeleteUser` have no service or handler consumer; the module's public surface is missing the endpoints they imply.
- **Issue:** Both repository methods (and their sqlc queries) are unreferenced outside the repository. There is no `GET /v1/users`, no `DELETE /v1/users/{id}`, no password change, and no tenant provisioning — `CreateTenant` is reachable only from `tests/testsuite`. `entity.Tenant` is referenced only by test fixtures.
- **Failure scenario:** A team adopts the framework and finds the reference auth module cannot complete its own primary flow: to register the first user they must hand-write an `INSERT INTO tenants` against the admin role, because no code path creates a tenant. Meanwhile the untested, unexercised `DeleteUser` is the method a GDPR erasure worker will reach for, and its behavior (hard delete, no audit event, no cascade check) has never run.
- **Suggestion:** Either wire these into service methods plus admin-guarded operations (with the role check the `RoleAdmin` constant implies), or delete them and the corresponding sqlc queries until there is a caller. Dead surface in a reference module is copied 50 times.

[SUGGESTION] [DESIGN] internal/modules/auth/entity.go:12 — `RoleAdmin` is declared but never assigned by any code path.
- **Issue:** `Register` hardcodes `Role: RoleMember` (service.go:61) and no update path exists, so every user in every tenant is a member forever. `platform/auth.HasRole` additionally special-cases the string `"superadmin"`, which `Role` does not define at all.
- **Failure scenario:** A downstream team adds `if !principal.HasRole("admin") { return ErrForbidden }` to an admin operation, reasonably assuming the constant is reachable. The gate is permanently closed for every user, and the only workaround discovered under pressure is a manual `UPDATE users SET role='admin'` in production.
- **Suggestion:** Assign `RoleAdmin` to the first user of a new tenant as part of the tenant-provisioning flow, add a role-change service method, and reconcile the `"superadmin"` string in `platform/auth` with the `Role` constants.

[SUGGESTION] [CLARITY] internal/modules/auth/service.go:121 — `VerifyPassword`'s error is collapsed into `ErrInvalidCredentials`, discarding operational failures with no log line.
- **Issue:** `if err != nil || !match` treats `ErrInvalidHash` and `ErrIncompatibleVersion` (argon2id.go:15-17) exactly like a wrong password. The module emits no `slog` output anywhere, so the distinction is lost entirely.
- **Failure scenario:** A data migration or a seeder writes rows whose `password_hash` is a bcrypt string or a truncated Argon2 encoding. Every affected user gets a 401 on a correct password; the metrics show "elevated failed logins", support tells users to reset, and on-call has no signal distinguishing a bad-hash corruption incident from ordinary credential failures. Time to diagnosis is measured in hours.
- **Suggestion:** Keep returning `ErrInvalidCredentials` to the client, but branch first: on a non-nil error from `VerifyPassword`, log at `slog.Error` with `user_id` and `tenant_id` (never the hash or password) so the corruption is visible.

[SUGGESTION] [DESIGN] internal/modules/auth/handler.go:139 — `mapDomainError` is duplicated per module by the scaffolder, and its prologue duplicates `httperr.Transform`.
- **Issue:** The function is byte-for-byte structurally identical to `orders/handler.go:213`, and `cmd/clericot/main.go:350` emits another copy for every scaffolded module. The `if err == nil` / `errors.As(&prob)` prologue (lines 140-147) is redundant: `httperr.Transform` already performs both checks.
- **Failure scenario:** The 23505 and 23503 gaps identified above are not one bug but N: fixing them requires editing every module plus the scaffolder template, and any module generated before the template fix keeps the old mapping. A team that fixes `auth` and forgets `orders` ships inconsistent status codes for the same class of database error.
- **Suggestion:** Move a table-driven mapper into `platform/httperr` (`httperr.MapSentinels(err, map[error]func(string) *Problem{...})`) that also classifies common `pgconn.PgError` codes centrally, and have each module supply only its sentinel table. Drop the redundant prologue.

[NITPICK] [SECURITY] internal/modules/auth/entity.go:22 — `User.PasswordHash` is on the domain entity with no `json:"-"`, and hash-bearing entities are returned to the transport layer.
- **Issue:** `Register`, `Login`, and `GetMe` all return `*User` including `PasswordHash`; `User` carries no json tags, so `json.Marshal` of the entity emits the Argon2 encoding under `"PasswordHash"`. The current handlers project into explicit response structs, so nothing leaks today.
- **Failure scenario:** A downstream module copies this shape and writes `resp.Body = user` or logs `slog.Info("user", "user", user)` for debugging. The full Argon2id encoding (params + salt + hash) lands in an API response or a log aggregator, giving anyone with log access an offline cracking target.
- **Suggestion:** Tag it `json:"-"`, or return a `PasswordHash`-free `User` from `GetMe` and keep the credential material on a separate `credentials` value object that only the repository and service handle.

### Strengths
- Argon2id hashing is deliberately performed *outside* `RunInTx` on register (service.go:38) and *after* the transaction commits on login (service.go:120). This keeps ~100ms of 64MB CPU work off a pooled database connection and avoids idle-in-transaction pileups under load. It is the non-obvious correct choice and worth preserving as the copied pattern.
- The repository layer is clean: every method resolves its executor through `txManager.GetDB(ctx)` so it works identically inside and outside a transaction, and `toDomainUser` maps `sqlcgen.Users` to a pure entity, so no `pgx`/`pgtype` type ever reaches `service.go`. This is exactly the contract project-layout.md specifies.
- `entity.go` genuinely has zero persistence and zero transport imports, and `service.go` touches no raw SQL and no `net/http`. The 6-file boundary is respected in the direction that is hardest to hold.
- Every service entrypoint wraps its work in `RunInTx` under `tenant.WithTenant`, so the RLS `set_config` hook always fires and no query can accidentally run unscoped against the pool. Handlers stay thin, with DTO mapping only and a single error-translation point.

### Out-of-slice observations
- `auth_test.go` covers only the sequential happy path: no concurrent registration, no case-variant email, no invalid-tenant input, no HTTP-level exercise of `mapDomainError`, and it passes `nil` for the API so `RegisterRoutes` is never executed by any test.
- `internal/platform/router/router.go` registers no Huma `SecurityScheme` and mounts no rate-limiting middleware, so `security.RateLimiter` is dead code repo-wide despite Rules 9 and 12.
- `TokenService.HTTPMiddleware` (token.go:130) silently swallows invalid/expired tokens and continues unauthenticated, which is only safe if every operation declares a security scheme — none do.
- `worker.go`'s `UserRegisteredJobArgs` and `TypeUserWelcomeEmail` have no producer anywhere in the repository.
- No production code path creates a tenant; `CreateTenant` is reachable only from `tests/testsuite` and `tenant_test.go`, so the reference registration flow cannot be completed by a fresh deployment without manual SQL.
- `platform/auth.HasRole`/`HasTenantAccess` grant blanket access to the role string `"superadmin"`, which `auth.Role` never defines and no code assigns.
- `internal/config/config.go` is also not gofmt-clean, suggesting no formatting gate exists in CI.
