**[CRITICAL] [SECURITY] internal/platform/router/router.go:32 — CORS reflects any origin back while allowing credentials.**
- **Issue:** `AllowedOrigins: []string{"https://*", "http://*"}` combined with `AllowCredentials: true`. In `go-chi/cors` v1.2.2, `allowedOriginsAll` is set only for the literal `"*"`; a wildcard *pattern* takes the `else` branch at cors.go:270/321, which writes `Access-Control-Allow-Origin: <the request's Origin>` verbatim plus `Access-Control-Allow-Credentials: true`. Every origin on the internet matches `https://*` or `http://*`, so this is the reflect-any-origin-with-credentials misconfiguration that the CORS spec forbids expressing with `*`. `X-CSRF-Token` is also in `AllowedHeaders`, so an attacker page can read a CSRF token from a response and replay it.
- **Failure scenario:** `evil.example` runs `fetch("https://api.tenant.com/orders", {credentials:"include"})`. The API answers `Access-Control-Allow-Origin: https://evil.example` + `Allow-Credentials: true`, so the browser hands the full tenant order list to attacker JavaScript. Today the primary cookie path is partly mitigated because `internal/platform/auth/session.go:20` pins `SameSite=Strict` — but the router has no knowledge of that and does not enforce it. The moment a downstream app sets `SameSite=None` (the normal choice for the cross-origin SPA that this CORS policy exists to serve), adds a second cookie, sits behind a proxy-SSO cookie, or uses mTLS, this becomes unauthenticated cross-origin data exfiltration. Shipping it as the framework default means every scaffolded service inherits it.
- **Suggestion:** Drive allowed origins from config (`cfg.App.AllowedOrigins`, comma-separated exact origins), default to empty in production, and hard-fail at startup if `AllowCredentials` is true while any entry contains `*`. If a wildcard is genuinely needed, use `AllowOriginFunc` with a suffix match on a configured apex domain.
- **Test contradiction:** `internal/platform/router/router_test.go:16` exercises `/livez`, `/readyz`, `/openapi.json` with no `Origin` header. `cors.Handler` returns early when `Origin` is absent, so no CORS header is ever produced and no assertion touches this policy.

**[CRITICAL] [DESIGN] internal/platform/app/coordinator.go:92,102,136 — every phase deadline is derived from the caller's context, so a cancelled context collapses the entire graceful shutdown to zero.**
- **Issue:** Phases 2, 3 and 4 all build their budgets with `context.WithTimeout(ctx, …)` where `ctx` is whatever the caller passed. `context.WithTimeout` on an already-Done parent yields an already-expired context. Nothing in `Shutdown` detaches from the parent, even though Rule 5 establishes `context.WithoutCancel` as the project idiom for exactly this class of detached cleanup.
- **Failure scenario:** A downstream service scaffolded from this template uses the standard Go idiom `ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM); defer stop(); <-ctx.Done(); coordinator.Shutdown(ctx)`. On SIGTERM, `ctx` is already Done. `httpServer.Shutdown(httpShutdownCtx)` returns `context.Canceled` immediately and force-closes every in-flight request mid-response; `riverClient.Stop(workerCtx)` aborts without waiting for running jobs (partial outbox work); `tracerProvider.Shutdown(otelCtx)` flushes nothing so the spans describing the crash are lost. The coordinator then logs `"shutdown complete within budget. process exiting cleanly."` The only reason `cmd/api` escapes this is that it happens to use a `sigChan` + `context.WithCancel` that is never cancelled before line 142 — an accident of style, not a guarantee.
- **Suggestion:** First statement of `Shutdown` should be `ctx = context.WithoutCancel(ctx)`, followed by a single `ctx, cancel := context.WithTimeout(ctx, 25*time.Second)` that all phases derive from, so the budget is actually enforced rather than being a log string.

**[SUGGESTION] [DESIGN] internal/platform/httperr/problem.go:22,42-107 — `Instance` is never populated and `Type` carries no information beyond `Status`.**
- **Issue:** Every constructor hardcodes a `Type` URI pointing at the generic RFC 9110 section for that status code, and no constructor or middleware ever sets `Instance`. RFC 9457 §3.1.1 exists so clients can dispatch on a stable problem *identity*, and §3.1.4 exists so a specific occurrence can be correlated.
- **Failure scenario:** A mobile client wants to show "that email is taken, sign in instead" for a registration conflict but a generic retry dialog for an order-number conflict. Both arrive as `status: 409` with the identical `type: ".../rfc9110#section-15.5.10"` and only a free-text `Detail`, so the client is forced to string-match English prose that changes the moment `err.Error()` is reworded upstream. Separately, a user reports "I got an error at 14:32" — with `Instance` empty and no request ID echoed in the body, there is no key to search the logs with.
- **Suggestion:** Add a `Code string \`json:"code,omitempty"\`` extension member (or per-module type URIs like `https://errors.<app>/orders/duplicate-number`) that modules populate from their sentinels, and have the router or a `WithInstance` helper set `Instance` from `middleware.GetReqID`.

**[SUGGESTION] [BUG] internal/platform/app/stream.go:20-27 — `Register` silently overwrites duplicate IDs and can re-register after `CloseActiveStreams` has run.**
- **Issue:** `Store` overwrites without reporting, and there is no terminal flag — after `CloseActiveStreams` drains the map, a subsequent `Register` succeeds and its closer is never invoked.
- **Failure scenario:** Two. (1) An SSE handler keys connections by user or tenant ID (the natural choice given `Register(id string, …)` and no documented uniqueness requirement). A user opens a second tab; the second `Register` replaces the first entry, so the first connection's closer is lost and the stream is orphaned until the client times out. (2) A request arrives in the ~100 ms window between Phase 1's readiness flip and Phase 2's teardown; its handler calls `Register` a microsecond after `CloseActiveStreams` finished its `Range`. That connection receives no close frame and never goes idle, so `httpServer.Shutdown` burns the entire 8 s Phase 2 budget waiting for it before force-closing.
- **Suggestion:** Have `Register` return the generated ID (or an error on collision) and add a `closed atomic.Bool` that `CloseActiveStreams` sets; when set, `Register` should immediately invoke the closer and return false so the handler can terminate itself.

**[NITPICK] [CLARITY] cmd/api/main.go:31 — the log level is read via `os.Getenv("APP_LOG_LEVEL")` four lines before `config.Load()` parses the identical variable into `cfg.App.LogLevel` (config.go:25).** Two sources of truth for one setting, and it bypasses the typed-config discipline of Rule 15. If bootstrap logging must precede config load, call `config.Load()` first and log the failure with a default logger.

**[NITPICK] [BUG] cmd/api/main.go:129-135 — `os.Exit(1)` inside the listener goroutine bypasses the coordinator entirely.** If `ListenAndServe` fails after startup (for example the listener is closed by something other than `Shutdown`), the process exits immediately without draining workers, flushing telemetry, or closing the DB pool. Send the error to a channel that the `select` on line 140 also watches, so the failure path runs `coordinator.Shutdown` too.

**[NITPICK] [DESIGN] internal/platform/app/coordinator.go:76 — `Shutdown` returns nothing, so callers cannot distinguish a clean exit from a degraded one.** Every phase error is swallowed into a log line, and `main` unconditionally falls off the end with exit code 0. Return an aggregated error (or a `ShutdownReport`) so `cmd/api` can `os.Exit(1)` when a phase overran its budget — which is the signal an operator needs to correlate with a truncated deploy.

### Strengths
- **Phase ordering is genuinely correct.** Streams are closed *before* `httpServer.Shutdown` (coordinator.go:88-94), which matters because hijacked and streaming connections never become idle and would otherwise pin `Shutdown` for its full timeout. Workers stop after the HTTP tier, telemetry flushes before the pools close, and the DB pool closes last — that dependency order is easy to get wrong and this gets it right.
- **Readiness draining is cleanly separated from dependency health.** The `atomic.Bool` short-circuit in `ReadyHandler` (health.go:67-72) means the drain response does not depend on the checker still being alive or on any I/O succeeding, and it returns a distinguishable `DRAINING` body rather than a generic 503. Using `alexliesenfeld/health` with `WithPeriodicCheck` for the deep checks also correctly protects the pool from probe storms, exactly as Rule 13 intends.
- **Every dependency in `Coordinator.Shutdown` is nil-guarded,** which is what lets one coordinator serve both the API and worker binaries with genuinely different subsystem sets. The design instinct — one lifecycle sequencer, many optional participants — is right; only the constructor's shape lets it down.
- **`httperr` keeps transport concerns out of the domain.** Modules map sentinels to problems at the handler edge via `mapDomainError`, and `Transform`'s default branch correctly refuses to leak internal error text to clients. The redaction boundary is in the right place; it just needs to log what it redacts.
