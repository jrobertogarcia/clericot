### D. Findings

**[CRITICAL] [DRIFT] docs/architecture/project-layout.md:17 — Documented database env var names do not exist; the real ones are `DB_`-prefixed, so a correctly-followed deployment silently falls back to the committed superuser localhost DSN.**
- **Issue:** `internal/config/config.go:13` sets `envPrefix:"DB_"` on the `Database` struct, so the effective variables are `DB_DATABASE_URL` and `DB_ADMIN_DATABASE_URL` (confirmed by `internal/config/config_test.go:31` using `DB_MAX_CONNS`). Both `docs/architecture/project-layout.md:17` and `docs/architecture/stack-standards.md:20` say `DATABASE_URL` / `ADMIN_DATABASE_URL`. `README.md:94-95` gets it right, so the docs also contradict each other. There is no `required` tag and no post-parse validation, so an unrecognized variable produces no error.
- **Failure scenario:** A platform engineer adopting Clericot reads the stack-standards row on Database Roles, provisions an unprivileged role, and sets `DATABASE_URL=postgres://app_user:...@prod-db/app`. `env.Parse` ignores it, `config.Load()` returns no error, `database.NewPool` dials the default `postgres://postgres:postgrespassword@localhost:5432/clericot`. In a container with no local Postgres the app crash-loops with a confusing "failed to ping database"; on a host that *does* have a local Postgres (a dev box, a sidecar), it connects as superuser to the wrong database and every RLS policy in `sql/migrations/0002_rls.sql` and `0004_orders.sql` is bypassed silently, because those policies are scoped `TO app_user` and superusers ignore RLS.
- **Suggestion:** Amend both architecture docs to the real names, and additionally fix the code by adding `required` tags (or an explicit production-env check) to `DatabaseConfig.URL`. The doc fix alone leaves the silent-fallback hazard; the config change is what converts a misconfiguration into a startup failure instead of a tenancy breach.

**[CRITICAL] [DRIFT] docs/architecture/stack-standards.md:20 — The dual-role database architecture is documented as a live guarantee but exists in no running binary; the RLS policies it underpins are therefore inert by default.**
- **Issue:** The row and `§2.2:60` promise `DATABASE_URL` → unprivileged `app_user` (RLS enforced) and `ADMIN_DATABASE_URL` → `postgres` for migrations. `docs/guidelines/distilled-lessons.md:8` states this as a **must**. In reality `cfg.Database.AdminURL` (`internal/config/config.go:30`) has zero readers, both DSNs default to the same superuser string, and migrations run on the application pool in both entrypoints (`cmd/api/main.go:51,59`; `cmd/worker/main.go:41,50`). Only `tests/testsuite/suite.go:29-33,103` actually builds two pools — so the test suite proves a property production never has.
- **Failure scenario:** A team ships to production having set only the (correctly-named) `DB_DATABASE_URL` to an `app_user` DSN, trusting the doc that migrations use the admin DSN. The first deploy runs `MigrateUp` on the app pool as `app_user`, which lacks `CREATE ROLE` and `ALTER TABLE ... FORCE ROW LEVEL SECURITY` privileges; the deploy fails on `0002_rls.sql`. The team's fix under time pressure is to point `DB_DATABASE_URL` back at the superuser, which makes the deploy succeed and permanently disables cross-tenant isolation for every request — with green tests and a doc that says isolation is enforced at the engine level.
- **Suggestion:** Fix the code — read `AdminURL`, open a second short-lived pool for `MigrateUp`, and close it before serving. The doc describes the correct design; amending it to match the code would mean writing down that migrations run as the application role, which contradicts `distilled-lessons.md:8` and Rule 4.

**[CRITICAL] [DRIFT] docs/architecture/stack-standards.md:21 — "Postgres advisory locking" on migrations is claimed twice and implemented nowhere, while every replica runs migrations on boot.**
- **Issue:** `internal/platform/database/migrations.go:35` uses goose's global `goose.UpContext`, which takes no lock. Advisory locking in goose v3 is opt-in via `goose.NewProvider(..., goose.WithSessionLocker(...))`; no `SessionLocker`, `NewProvider`, or `pg_advisory_lock` appears anywhere in the repo. Both `cmd/api/main.go:59` and `cmd/worker/main.go:50` call `MigrateUp` unconditionally at startup.
- **Failure scenario:** A Kubernetes rollout starts three `api` pods and two `worker` pods simultaneously. All five call `MigrateUp` against the same database within milliseconds. Goose reads `goose_db_version`, all five see the same pending version, and all five attempt to apply it. The winner commits; the losers fail with duplicate-object or duplicate-key errors and `os.Exit(1)`, producing a crash-looping rollout. With a partially-transactional migration, the database can be left mid-migration. The doc tells the reader this is already handled, so nobody adds an init-container or a migration Job.
- **Suggestion:** Fix the code — switch `MigrateUp` to `goose.NewProvider` with `lock.NewPostgresSessionLocker()`. Amending the doc instead would leave a template whose default deployment shape (migrate-on-boot in every replica) is unsafe.

**[CRITICAL] [GAP] docs/architecture/stack-standards.md:12 — `SecuritySchemes` is claimed in three separate places and implemented nowhere, so the published OpenAPI document advertises every endpoint as public.**
- **Issue:** `stack-standards.md:12`, `:28`, and `§2.5:75` all assert Huma OpenAPI `SecuritySchemes` integration. `internal/platform/router/router.go:54-58` builds `huma.DefaultConfig` and never touches `Components.SecuritySchemes`; no `huma.Operation` in `internal/modules/auth/handler.go` or `internal/modules/orders/handler.go` sets `Security`. Authentication is a best-effort context decoration (`internal/platform/auth/token.go:130`, which swallows the error) plus per-service nil checks.
- **Failure scenario:** A downstream team generates a TypeScript client from `/openapi.json` and an API gateway policy from the same document. Because no operation declares security, the generated client sends no `Authorization` header and the gateway classifies `POST /v1/orders` as unauthenticated and exempt from token validation. The request reaches the service, `PrincipalFromContext` returns nil, and the caller gets a 401 they cannot explain from the spec — or, on any future endpoint whose service forgets the nil check, gets served.
- **Suggestion:** Fix the code — register a `bearerAuth` scheme in `NewRouter` and set `Security` on non-public operations. The doc states the intended contract correctly and three times; weakening it would remove the only written record that these endpoints are meant to be protected.

**[CRITICAL] [DRIFT] docs/architecture/stack-standards.md:13 — `application/problem+json` is never emitted; domain errors are served as `application/json`, and the API returns two different error content types for the same endpoint.**
- **Issue:** Huma selects the problem media type only for response bodies implementing `huma.ContentTypeFilter` (`huma@v2.39.1/huma.go:661`, `error.go:129-144`). `internal/platform/httperr/problem.go` implements `Error()` and `GetStatus()` only — no `ContentType(string) string` and no `ErrorDetail()`, so the documented `huma.ErrorDetailer` claim (`stack-standards.md:13` and `§2.1:52`) is also false. Huma's *own* validation errors use `huma.ErrorModel`, which does implement the filter. `internal/platform/httperr/httperr_test.go` asserts only status codes, so nothing catches this.
- **Failure scenario:** A client of `POST /v1/auth/register` writes one error branch keyed on `Content-Type: application/problem+json`, as the Golden Rules and stack standards promise. A password shorter than 8 chars trips huma's JSON Schema validation and returns `application/problem+json` — handled. A duplicate email reaches `mapDomainError` → `httperr.NewConflict` and returns the byte-identical JSON body under `application/json` — the client's content-type branch misses, and a 409 surfaces as an unparsed generic failure. The behavior is inconsistent within a single endpoint, which makes it look like an intermittent bug rather than a missing method.
- **Suggestion:** Fix the code — add `func (p *Problem) ContentType(ct string) string` mirroring `huma.ErrorModel.ContentType`, and drop or implement the `ErrorDetailer` claim. This is a four-line change that makes two documents true; amending the docs would abandon Rule 2's central promise.

**[IMPORTANT] [SPEC] docs/architecture/stack-standards.md:22 — Rule 7's 5-minute River retention and the "immutable compliance audit trail" are mutually exclusive as written: the audit record has no durable store.**
- **Issue:** `stack-standards.md:24` designates River-outbox-staged `audit.event.v1` CloudEvents as the SOC 2 / HIPAA / ISO 27001 record. `stack-standards.md:22` and `golden-rules.md:26` mandate 5-minute River retention.
