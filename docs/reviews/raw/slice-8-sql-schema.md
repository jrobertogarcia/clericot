[SUGGESTION] [DESIGN] /Users/robertogarcia/src/clericot/sql/migrations/0001_init.sql:3-4 — `VARCHAR(64)` identifiers with no format or non-empty constraint, where `uuid` is the natural type.

A client pages `LIMIT 20 OFFSET 0` then `LIMIT 20 OFFSET 20`; because the tie order can differ between the two executions (different plans, different worker counts), one of the tied rows appears on both pages and another appears on neither. Deep offsets compound the cost, since `OFFSET 100000` still sorts 100020 rows.
- **Suggestion:** Add `id` as a tiebreaker (`ORDER BY created_at DESC, id DESC`) and move to keyset pagination (`WHERE (created_at, id) < ($2, $3)`), which pairs with the composite index recommended above. Consider defaulting `created_at` to `NOW()` server-side rather than accepting it from the client.

### Strengths
- The base policy is a single **permissive** `FOR ALL TO app_user` policy with both `USING` and `WITH CHECK` clauses, exactly as `distilled-lessons.md` §1 prescribes. Getting `WITH CHECK` right matters: without it, `INSERT`/`UPDATE` could write rows into other tenants even while reads were correctly filtered, and many RLS implementations miss this.
- Using `current_setting('app.current_tenant_id', true)` compared against a `NOT NULL` column fails **closed** when the session variable is unset — NULL comparison yields NULL, which is neither a passing `USING` nor a passing `WITH CHECK`. Combined with transaction-local `set_config` (`tenant.go:41`), a pooled connection cannot leak a previous request's tenant scope. The `true` (missing_ok) argument is also what makes migrations and system paths not crash outright.
- The `DO $$ ... $$` block in `0002:2-10` is correctly bounded by `-- +goose StatementBegin/End`, and it is the only block in the four migrations that needs them — the `CREATE POLICY` statements contain no internal semicolons. The trap documented in `distilled-lessons.md` §2 was correctly identified and correctly scoped.
- Every sqlc query carries an explicit `AND tenant_id = $N` predicate on top of the RLS policy. That redundancy is genuinely valuable defense-in-depth: it keeps queries correct if they are ever run on the admin pool, and it gives the planner a usable index qual that the RLS security qual alone would not.
- The `uq_tenant_user_email UNIQUE (tenant_id, email)` constraint scopes uniqueness per tenant rather than globally — the right call for multi-tenancy, and one that is frequently gotten wrong in the global direction.
