[IMPORTANT] [BUG] /Users/robertogarcia/src/clericot/internal/platform/events/middleware.go:43-56 — PoisonQueue is registered inside Retry, so retries never happen and every transient error is dead-lettered on the first attempt.
- **Issue:** Watermill applies router middleware so that the first-added is outermost (`watermill@v1.5.3/message/router.go:652`: "first added middlewares should be executed first (so should be at the top of call stack)"). The order here is Idempotency → Retry → PoisonQueue → handler. `poisonQueue.Middleware` (`poison.go:88-93`) publishes the failed message and then sets `err = nil`, so `middleware.Retry` always observes success and its `MaxRetries: 3` / backoff configuration is dead code. Rule 7 and `stack-standards.md` both say PoisonQueue routes *persistent* failures.
- **Failure scenario:** A handler hits a 50ms Postgres connection blip on one message. Instead of the configured 3 retries with 100ms→2s backoff, the message is published to `events:dlq:poisoned` immediately and acked. During a 30-second database failover, the entire in-flight event stream lands in the DLQ, none of it retried, and (per the finding below) the DLQ is itself lossy and unread.
- **Suggestion:** Add PoisonQueue before Retry so the chain is Idempotency → PoisonQueue → Retry → handler, letting retries exhaust before dead-lettering. Consider `middleware.PoisonQueueWithFilter` so transport-level and validation errors route differently.

[IMPORTANT] [BUG] /Users/robertogarcia/src/clericot/internal/platform/events/middleware.go:20-32 — The idempotency key is claimed before execution and never released on failure, turning crashes into silent permanent message loss.
- **Issue:** `SetNX(key, "1", 24h)` is taken *before* `h(msg)` and is never deleted when the handler errors or the process dies. The doc comment states "at most once", but Rule 7 positions this as the mandatory consumer guard for an at-least-once outbox relay, and the PEL reclaim configured in `factory.go` exists precisely to redeliver messages from crashed workers.
- **Failure scenario:** Worker pod claims key `idempotency:events:<uuid>`, begins handling, then the node is OOM-killed mid-handler. After `MaxIdleTime` (2m) the message is reclaimed from the PEL by a surviving pod. The middleware's `SetNX` returns false, the middleware returns `nil, nil`, the message is acked and deleted. The reclaim machinery works perfectly and the message is dropped anyway, with no log and no DLQ entry. Every worker restart during traffic silently loses the in-flight window.
- **Suggestion:** Use a two-phase marker: `SET NX` a short-lived `processing` value, upgrade to `done` with the full TTL only after the handler succeeds, and `DEL` (or let the short TTL expire) on failure. At minimum, `DEL` the key in a deferred branch when the handler returns an error, and log at Warn when a duplicate is discarded so drops are observable.
- **Test contradiction:** `TestIdempotencyMiddleware_NoRedis` passes a nil `*redis.Client`, which hits the `if rdb == nil { return h(msg) }` early return at line 17. The Redis-backed path — the only path where the key is ever set — is not executed by any test.

[IMPORTANT] [DESIGN] /Users/robertogarcia/src/clericot/internal/platform/events/factory.go:51 — A single hardcoded consumer group for all topics and all consumers makes independent handlers steal each other's messages.

### Strengths
- The publisher's `DefaultMaxlen: 100_000` genuinely maps to `XADD ... MAXLEN ~` (verified: `redisstream/publisher.go:93-97` sets `Approx: true`), so stream trimming is both bounded and cheap — the spec is implemented correctly rather than nominally.
- `relay.go:27` uses the stable `job.Args.ID` as the Watermill message UUID rather than generating a fresh one. This is the subtle, correct choice: River-side retries of the relay job republish an identical dedup key, which is exactly what a `SET NX` consumer guard needs to work. Whoever wrote this understood the outbox contract.
- The write half of the outbox is genuinely atomic. `orders/service.go` performs `riverClient.InsertTx` and `audit.StageAuditLog` inside the same `RunInTx` closure as the business writes, so the event row commits or rolls back with the order. The dual-write problem is correctly avoided; the defects are all downstream of the commit.
- Coordinator phase 3 stops River, Asynq, and the Watermill router concurrently under one shared 10s `context.WithTimeout` and a `WaitGroup`, rather than serially consuming three separate budgets — the right shape for the Rule 13 25-second envelope.
- Nil-tolerance is consistent and non-panicking across the slice (`IdempotencyMiddleware` with nil Redis, `ConfigureSubscriberRouter` with a nil DLQ publisher, worker constructors defaulting to `slog.Default()`). The problem is silence, not crashes — the degradation paths just need to be loud.
