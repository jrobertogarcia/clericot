## Slice 1: Transaction & tenancy core
**Files reviewed:** 7 | **Findings:** 2 critical, 6 important, 5 suggestion, 3 nitpick

### Findings

[CRITICAL] [SECURITY] internal/platform/tenant/middleware.go:19 — `X-Tenant-ID` is accepted without any authorization check when the principal is nil.
- **Issue:** The guard is `if principal != nil && !principal.HasTenantAccess(headerTenant)`. When `principal == nil` the entire ACL check short-circuits to false and the attacker-supplied header becomes the request's tenant scope. `TokenService.HTTPMiddleware` (internal/platform/auth/token.go:126-136) is a populate-if-present middleware that silently ignores absent, malformed, expired, and Redis-revoked tokens and never rejects, so `principal == nil` is reachable on every route.
- **Failure scenario:** `POST /v1/widgets` with header `X-Tenant-ID: acme-corp` and no `Authorization` header. Scaffolder-generated handlers (cmd/clericot/main.go:327-330) take the tenant from `input.Body.TenantID` falling back to `tenant.FromContext(ctx)`, with no principal check; the generated service calls `RunInTx(tenant.WithTenant(ctx, dto.TenantID))`. `set_config('app.current_tenant_id','acme-corp', true)` is applied, the RLS `USING`/`WITH CHECK` predicates both pass, and an unauthenticated caller reads and writes another tenant's rows.
- **Suggestion:** Return 401 when a tenant header is present and `principal == nil`; make `HasTenantAccess` unconditional rather than nil-guarded. Additionally require the middleware to be mounted after a rejecting auth middleware.
- **Test contradiction:** `TestTenantMiddleware` (tenant_test.go:32-72) has three cases, all of which inject a non-nil `AuthPrincipal` via `auth.WithPrincipal` before calling the handler. The nil-principal + header combination is never exercised. No integration test trips it either, because the one module that exists (`orders`) independently rejects `principal == nil` in its service layer — a check the scaffolder does not reproduce.

[CRITICAL] [BUG] internal/platform/tenant/worker.go:87-97 — GDPR purge silently scrubs zero user rows when the tenant is not `status='active'`, then permanently locks the data away.
- **Issue:** Phase 1 runs as `app_user` under RLS. Policy `tenant_isolation_users` (sql/migrations/0002_rls.sql) requires `EXISTS (SELECT 1 FROM tenants WHERE id = tenant_id AND status = 'active')`. The `UPDATE users` result is discarded (`if _, err := db.Exec(...)`), so zero-rows-matched is indistinguishable from success. The subsequent `UPDATE tenants SET status='deleted'` then makes the rows unreachable to `app_user` forever.
- **Failure scenario:** The operational flow the docs describe (stack-standards.md §2.3: `status = 'active'` "enabling instant workspace suspension") is suspend-then-delete. An admin suspends tenant `acme` (`status='suspended'`), then enqueues `tenant:purge`. The scrub `UPDATE` matches 0 rows and returns no error; the tenant flips to `deleted`; `ProcessTask` returns nil and Asynq records the erasure as complete. Every user's real email, name, and Argon2id password hash remains in `users` indefinitely, and no `app_user` transaction can ever reach those rows again to retry. Silent GDPR right-to-erasure failure with an audit trail that claims success.
- **Suggestion:** Inspect `CommandTag.RowsAffected()` and fail the task on an unexpected zero; assert the tenant's pre-purge status inside the transaction; or grant the purge path a policy admitting `status IN ('active','suspended')` (or run Phase 1 under a dedicated privileged role) so suspension does not block erasure.
- **Test contradiction:** `TestPurgeTenantWorker_ProcessTask` (worker_test.go:41-56) seeds tenant A with `Status: "active"` and only ever purges an active tenant. `TestPostgresRLS_TenantIsolation` (tenant_test.go:105-114, 182-190) independently proves the exact mechanism — suspended tenant C reads 0 rows — but the two scenarios are never combined, and the worker path asserts nothing about rows affected.

[IMPORTANT] [SECURITY] internal/platform/database/tx.go:39-65 — Nested `RunInTx` ignores the tenant in its own context; savepoints silently inherit the root transaction's `set_config`.
- **Issue:** `TenantSetter` is invoked only on the root path (line 84). The savepoint branch neither re-applies `set_config` (it cannot meaningfully — the GUC is transaction-scoped, not savepoint-scoped) nor validates that `FromContext(ctx)` matches the tenant the root transaction was opened with. The mismatch is accepted silently.
- **Failure scenario:** A cross-tenant batch service opens `RunInTx(tenant.WithTenant(ctx, "tenant-a"), ...)` and inside, per affected tenant, calls `RunInTx(tenant.WithTenant(txCtx, "tenant-b"), ...)`. The nested call issues `savepoint sp_1` but `app.current_tenant_id` is still `tenant-a`. Reads inside the nested block return tenant A's rows while every line of calling code says `tenant-b`; writes stamped `tenant_id='tenant-b'` fail the `WITH CHECK` with an opaque RLS violation instead of the tenant switch being refused up front.
- **Suggestion:** Store the root tenant alongside the `pgx.Tx` in the context value; in the nested branch, return an explicit error when `FromContext(ctx)` is non-empty and differs from the root tenant. A savepoint cannot safely change a transaction-local GUC, so refusing is the only correct behavior.
- **Test contradiction:** `TestTxManager_RunInTx_SavepointNesting` (database_test.go:99-170) passes `txCtx` straight through to the nested call, so the nested context always carries the same tenant as the root and the mismatch never arises.

[IMPORTANT] [DRIFT] internal/platform/database/migrations.go:35 — No advisory lock; concurrent replica boots race on migrations.
- **Issue:** stack-standards.md line 21 and §2.2 both claim migrations execute "with Postgres advisory locking." `goose.UpContext` is the package-level API and takes no locker. In goose v3.27.3, locking exists only through the Provider API — `provider_options.go:70-74` states plainly that if `WithSessionLocker` is not called, "locking is disabled."
- **Failure scenario:** `cmd/api/main.go:59` runs `MigrateUp` at process start. A Deployment with `replicas: 3`, or any rolling update, starts multiple pods concurrently and all of them run goose Up against the same database. Two pods read the same current version, both attempt `0005_x.sql`, and race on `goose_db_version` inserts plus concurrent DDL — producing duplicate version rows, a lock deadlock, or a half-applied migration that aborts the rollout.
- **Suggestion:** Move to `goose.NewProvider(goose.DialectPostgres, db, fsys, goose.WithSessionLocker(lock.NewPostgresSessionLocker()))`, or wrap the run in an explicit `pg_advisory_lock`/`pg_advisory_unlock` pair.

[IMPORTANT] [DRIFT] internal/platform/database/migrations.go:23 — `MigrateUp` has no admin-role contract, and the only application caller passes the RLS-enforced app pool.
- **Issue:** stack-standards.md line 20 mandates strict role separation: `DATABASE_URL` → unprivileged `app_user`, `ADMIN_DATABASE_URL` → `postgres` for migrations. `MigrateUp(ctx, pool, dir)` accepts any `*pgxpool.Pool` and documents no requirement. `config.DatabaseConfig.AdminURL` exists but has zero readers anywhere in the repo. `cmd/api/main.go:59` and `cmd/worker/main.go:49` pass the pool built from `cfg.Database`; only `tests/testsuite/suite.go:96` passes an admin pool.
- **Failure scenario:** Deploy exactly as the docs prescribe, with `DB_DATABASE_URL` pointing at the unprivileged `app_user`. Boot reaches `0002_rls.sql`, which needs `CREATE ROLE app_user` and `ALTER TABLE users FORCE ROW LEVEL SECURITY` — both require ownership or superuser. `app_user` gets `permission denied`, `MigrateUp` returns an error, and the API exits at main.go:61. The framework only boots today because the default `DATABASE_URL` is the `postgres` superuser — which, per distilled-lessons.md §1, also silently bypasses every RLS policy in the system.
- **Suggestion:** Change the signature to make the requirement unavoidable — take `config.DatabaseConfig` and open a short-lived pool from `AdminURL` internally, or rename to `MigrateUpAsAdmin(ctx, adminPool, dir)` with a doc comment stating the role requirement. Wire `cfg.Database.AdminURL` in both mains.

[IMPORTANT] [DESIGN] internal/platform/tenant/tenant.go:15-20 — `init()`-registered package globals make RLS enforcement depend on the import graph rather than on wiring, violating Rule 15 and project-layout §4.
- **Issue:** `database.TenantSetter` and `storage.TenantExtractor` are mutable package globals assigned as a side effect of `tenant.init()`. Because `database` cannot import `tenant` (import cycle), nothing at compile time or construction time guarantees the hook is installed. `TxManager` will happily run with `TenantSetter == nil` (tx.go:84 treats it as optional).
- **Failure scenario:** A downstream team writes `cmd/backfill` importing only `config` and `database`, then calls `database.NewTxManager(pool)`. `TenantSetter` is nil, `set_config` is never issued, and every `RunInTx` runs with `app.current_tenant_id` unset. On the shipped `users`/`orders` tables this is fail-closed (silent 0 rows that read as "not found"); on tables created by `clericot make:module` it is fail-open, because the scaffolder's `migrate create` template (cmd/clericot/main.go:55-60) emits an empty migration with no `ENABLE ROW LEVEL SECURITY` and no policy. The same import-order hazard applies to `storage.TenantExtractor`, whose default returns `""`, silently filing every tenant's uploads under `tenants/global/`.
- **Suggestion:** Make the hook a constructor parameter — define a small `SessionConfigurator` type in `database` and wire `database.NewTxManager(pool, tenant.SetTenantSession)` / `storage.NewStorageEngine(ctx, url, tenant.FromContext)` in each main. Missing wiring then fails to compile instead of failing open.

[IMPORTANT] [DESIGN] internal/platform/tenant/worker.go:83-123 — The purge is not atomic across phases and reports success when storage is unconfigured.
- **Issue:** Phase 1 commits before Phase 2 begins; Phase 2 is skipped entirely when `w.storage == nil` with no error and no log; and nothing persists purge progress, so an incomplete erasure is indistinguishable from a complete one after the fact.
- **Failure scenario:** `STORAGE_BUCKET_URL` is unset, or `storage.NewStorageEngine` fails at boot — both mains only `Warn` and continue with a nil engine (cmd/api/main.go:78-82). `ProcessTask` then scrubs the database, marks the tenant `deleted`, returns nil, and Asynq records a successful erasure while every uploaded PII document under `tenants/<id>/` remains in the bucket forever. Separately, when `DeletePrefix` fails permanently, Asynq exhausts retries and archives the task, but the tenant row already reads `deleted` and no query can distinguish "fully erased" from "database-only erased."
- **Suggestion:** Return an error when `w.storage == nil` rather than skipping the phase; purge blobs before flipping tenant status to `deleted`; and persist `purge_started_at`/`purge_completed_at` on `tenants` so incomplete erasures are queryable and re-drivable.

[IMPORTANT] [DESIGN] internal/platform/tenant/middleware.go:29-32 — The tenant the middleware resolves has no enforced consumer, so header-based tenant switching silently returns the wrong tenant's data.
- **Issue:** The middleware's only output is a context value, and every service in the repo discards it. `orders/service.go:158`, `:181`, and `:226` all re-derive scope with `tenant.WithTenant(ctx, principal.TenantID)`, overwriting whatever the middleware decided. The middleware's `HasTenantAccess` check therefore authorizes a tenant switch that never happens.
- **Failure scenario:** A user with `TenantID: "acme"` and `Tenants: ["acme","globex"]` sends `GET /v1/orders/search` with `X-Tenant-ID: globex`. The middleware validates access and sets the context tenant to `globex`. `SearchOrders` overwrites it with `principal.TenantID` = `acme`. The response is HTTP 200 containing acme's orders — a silent wrong-tenant answer rather than an error, in a UI where the user has explicitly switched workspaces.
- **Suggestion:** Make the middleware value authoritative: services should read `tenant.FromContext(ctx)` (which `RunInTx` already consumes) instead of `principal.TenantID`, and `RunInTx` should error when a tenant-scoped path has no tenant in context. Otherwise remove the header-switching branch entirely so the contract is not advertised.
- **Test contradiction:** `TestTenantMiddleware` asserts only on the context value observed by a stub handler that echoes `tenant.FromContext`. No test composes the middleware with a real service, so the override is invisible.

[SUGGESTION] [PERF] internal/platform/database/tx.go:40 — Unbounded savepoint nesting risks PostgreSQL subtransaction-cache overflow.
- **Issue:** pgx's `dbTx.Begin` issues `savepoint sp_N` with a monotonically increasing counter (pgx/v5 tx.go:170-176), and `Rollback` issues only `rollback to savepoint sp_N` (tx.go:322) without ever releasing. `RunInTx` bounds neither nesting depth nor the number of nested calls under one root transaction.
- **Failure scenario:** The natural framework idiom is a service opening one root `RunInTx` and calling a per-item helper that itself calls `RunInTx`. Importing 500 rows in one request assigns 500 subtransactions to the top-level transaction, overflowing the 64-slot subxid cache in `PGPROC`. Every other backend in the cluster then falls back to `pg_subtrans` SLRU lookups for visibility checks, causing cluster-wide latency degradation that persists for the life of the transaction. Nothing in the framework or docs warns against this.
- **Suggestion:** Track nesting depth in the context value and return an explicit error past a small bound (e.g. 8), and document the constraint on `RunInTx` so the pathology surfaces in development rather than in production under load.

[SUGGESTION] [CLARITY] internal/platform/database/tx.go:51,79 — Rollback errors are discarded with no logging or metric.
- **Issue:** Both deferred paths use `_ = tx.Rollback(rollbackCtx)`. A rollback failure is not benign: pgx responds by killing the connection (`tx.conn.die()`, pgx/v5 tx.go:216-219). The detached-context design exists precisely to make these rollbacks succeed, and there is no signal when it does not.
- **Failure scenario:** Under sustained client cancellation (mobile clients disconnecting mid-request), every root rollback fails against a connection pgx has already torn down, and the pool silently churns through reconnects. Operators observe elevated latency and connection counts with no log line, metric, or trace event anywhere to correlate against.
- **Suggestion:** Give `TxManager` a `*slog.Logger` and log rollback failures at warn level with the transaction kind (root vs savepoint) and whether the parent context was already canceled.

[SUGGESTION] [DRIFT] internal/platform/tenant/worker.go:70,74 — Permanently-malformed tasks are retried instead of quarantined, contrary to Rule 7.
- **Issue:** Both the unmarshal failure and the empty-tenant-ID check return plain errors. Asynq retries on any non-nil error unless it wraps `asynq.SkipRetry`. Rule 7 mandates poison-pill quarantine.
- **Failure scenario:** One task enqueued with a truncated payload retries under the default 25-attempt exponential backoff, occupying a worker slot and emitting 25 error-level log entries over roughly a day, before finally landing in the archive. Nothing about the payload can change between attempts, so every retry is guaranteed to fail identically.
- **Suggestion:** `return fmt.Errorf("failed to unmarshal tenant purge payload: %v: %w", err, asynq.SkipRetry)` for both deterministic validation failures.

[SUGGESTION] [DRIFT] internal/platform/tenant/worker.go:42-62 — `EnqueuePurgeTenant` sets no unique key, queue, retry budget, or timeout.
- **Issue:** Rule 7 requires idempotency guards on consumers and stack-standards.md line 25 lists "unique key tracking" as part of the Asynq tier. `asynq.NewTask(TypeTenantPurge, payload)` is enqueued with zero options, so nothing deduplicates or bounds the job.
- **Failure scenario:** An admin double-clicks "delete workspace," or a client retries a timed-out API call. Two purge tasks for the same tenant are picked up by two workers concurrently; both open Phase 1 transactions touching the same `users` and `tenants` rows, one blocks on the other's row locks for the full duration, then redundantly re-runs the entire scrub and a second `DeletePrefix` sweep across the bucket.
- **Suggestion:** `asynq.NewTask(TypeTenantPurge, payload, asynq.TaskID("tenant-purge:"+tenantID), asynq.Queue("critical"), asynq.MaxRetry(5), asynq.Timeout(10*time.Minute))`.

[SUGGESTION] [DRIFT] internal/platform/tenant/middleware.go:20 — The 403 response is served as `text/plain`, not `application/problem+json`.
- **Issue:** `http.Error` hardcodes `Content-Type: text/plain; charset=utf-8` and appends a newline, while the body is hand-written JSON. Rule 2 and stack-standards.md line 13 require RFC 9457 `application/problem+json` for all error contracts, and this body also omits the required `status` and `detail` members.
- **Failure scenario:** A generated OpenAPI client, or any consumer branching on `Content-Type == "application/problem+json"` — the exact contract `httperr.Problem` publishes for every other error in the system — fails to parse this one response and surfaces an opaque transport error to the user instead of "Tenant Access Denied."
- **Suggestion:** Set the header explicitly and construct the body through `httperr.Problem` so the tenancy layer's errors match the shape the rest of the API guarantees.

[NITPICK] [CLARITY] internal/platform/database/query.go:15 — `BuildSQL` is a zero-value passthrough whose doc comment overclaims.
- **Issue:** The body is exactly `bob.Build(ctx, q)` (bob v0.50.0 build.go:24) with an identical signature; it adds no validation, dialect pinning, or instrumentation. The comment claims it "enables dynamic multi-predicate queries that preserve PostgreSQL index scans (Rule 6)," but index-scan preservation comes from how callers construct predicates, not from this call.
- **Failure scenario:** A developer scaffolding a new search endpoint reads the comment, concludes `BuildSQL` provides an index-safety guarantee, and skips the `EXPLAIN ANALYZE` verification Rule 6 actually requires — shipping a sequential scan on a >50k-row table, the precise outcome Rule 6 exists to prevent.
- **Suggestion:** Either drop the wrapper and the `Expression` alias in favor of calling `bob.Build`/`psql` directly, or give it real substance (debug-level SQL logging, OTel span attribute) and correct the comment to describe what it does.

[NITPICK] [DRIFT] internal/platform/database/db.go:41-49 — Retry loop contradicts the documented shape and ignores context cancellation.
- **Issue:** distilled-lessons.md §4 specifies "5 attempts, 500ms"; the code does 10 attempts. `time.Sleep` is not context-aware and `ctx.Err()` is never checked between attempts.
- **Failure scenario:** At boot against an unreachable database, `NewPool` blocks for roughly 25 seconds (10 × 2s ping timeout + 9 × 500ms sleep) and ignores context cancellation throughout — so a SIGTERM during a failed rollout cannot interrupt it, consuming the entire 25-second shutdown budget Rule 13 defines before the process has even started.
- **Suggestion:** Check `ctx.Done()` in the loop and select on it instead of sleeping unconditionally; align the attempt count with the documented value or update the doc.

[NITPICK] [CLARITY] internal/platform/database/migrations.go:24-26,44-46,64-66 — The default `dir` value `"sql/migrations"` cannot resolve against the embedded filesystem.
- **Issue:** `sql/embed.go` uses `//go:embed migrations/*.sql` from inside package `sql`, so embedded paths are rooted at `migrations/`. All four call sites correctly pass `"migrations"` explicitly; the `""` fallback resolves to `"sql/migrations"`, which does not exist in the FS. The same wrong default is triplicated across `MigrateUp`, `MigrateDown`, and `MigrateStatus`.
- **Failure scenario:** A downstream developer calls `database.MigrateUp(ctx, pool, "")`, trusting the documented default, and receives `sql/migrations directory does not exist` — a confusing error, since that path does exist on disk in the repo and only the embedded FS lacks it.
- **Suggestion:** Default to `"migrations"`, or remove the default and require an explicit `dir`; factor the shared dialect/open/close boilerplate into one helper.

### Strengths
- The RLS design is genuinely fail-closed: `current_setting('app.current_tenant_id', true)` yields NULL when unset, so `tenant_id = NULL` denies rather than leaks, and `FORCE ROW LEVEL SECURITY` closes the table-owner bypass. Getting the default direction right is the single most important decision here.
- `SELECT set_config('app.current_tenant_id', $1, true)` is both parameterized (no injection through a tenant identifier) and transaction-local, which is the correct and frequently-botched answer to connection-pool contamination on a shared `pgxpool`.
- Detached rollback via `context.WithoutCancel(ctx)` plus a bounded 2s timeout, applied consistently to both the root and savepoint paths and driven by an explicit `committed` flag rather than error-sniffing after `Commit`. This is correct and rarely implemented properly.
- The `DBTX` interface keeps `pgx.Tx` out of domain and repository signatures while `GetTx` provides the narrow escape hatch River's `InsertTx` requires — a clean satisfaction of Rule 5's "without leaking `pgx.Tx` into domain signatures."
- `stdlib.OpenDBFromPool(pool)` with `defer db.Close()` is correct: the returned `*sql.DB` releases connections back to the `pgxpool` and closing it does not close the underlying pool (verified against pgx v5.10.0 stdlib/sql.go:237-242).
